# Security boundary and limitations

Client policy is enforced natively as a ceiling over each workspace's client-specific permissions. New pairings are read-only and cannot create automatic workspaces until configured in native Controls. Interaction, upload, download and saved-account capabilities are checked at admission, dispatch and asynchronous continuation; late results are withheld after permission revocation. Client resources may be inherited live, with workspace restrictions narrowing that selection. Account inheritance preserves exact HTTPS-origin grants, and inherited files retain final-path and file-identity checks. A Default-group grant covers each account the vault currently marks Default, at the origin the vault stores for it; Sensitive accounts need an individual grant. CEF download callbacks also gate downloads caused indirectly by agent-owned pages. Native configuration is unavailable through MCP.

Xenon is an unsigned, early Windows release. It separates MCP authorization, browser profiles and credential use, but it has not received an independent security audit. Its purpose is to prevent routine model/tool access to vault plaintext and to make browser authority explicit. It does not defend a Windows account from malware already running as that account, an administrator, a debugger or a compromised Chromium/CEF runtime.

## Local client authority

Uncertain-click collection is a separate native-human opt-in that starts off each process. It is not available through MCP and does not change filtering, authority or dispatch outcomes. It stores only allowlisted role/tag/reason enums, numeric geometry and boolean/numeric filter diagnostics for screenshot-bound primary agent clicks whose native hit ancestry matches a previously observed uncertain candidate. Both mouse dispatches must complete, and document, human activity, authority, private/authentication state and collection generation must still qualify. Collection excludes labels, URLs, page source, raw CSS, values, IDs, credentials and screenshots; there is no upload path. The fixed owner-only JSONL file is capped at 8 MiB. Native clear/disable invalidates pending collection; disable preserves existing records. File opening pins the data/diagnostics directories, rejects reparse points and multiply-linked files, and validates handles before any append or truncation. Records describe dispatch evidence rather than website success or a confirmed filtering error.

The browser serves a Windows named pipe with a protected current-user SID ACL and `PIPE_REJECT_REMOTE_CLIENTS`. The first listener claims the pipe name exclusively to detect another owner. A connected process must also pair through the native UI or authenticate with a previously issued token. A forged `clientId` inside page parameters is ignored; the authenticated connection establishes identity.

Private directories inherit current-user access to their descendants. This preserves browser access when Chromium adds sandbox capability permissions to its network-storage directories; it grants no additional user access. File and pipe ACLs remain non-inheritable.

The adapter stores the token in a separately protected configuration file. The broker stores its SHA-256 hash, not the token. Native-generated identifiers and tokens use the Windows cryptographic RNG. Configuration and browser data must remain private to their Windows user. Processes running as that same user can potentially access those files or the process itself; the pairing token is not a sandbox against local malware.

Authorization is per paired client and workspace, with separate account grants tied to client, workspace, account and exact HTTPS origin. A native Default-group grant on a client or workspace extends that to every account the human placed in the Default group, including accounts saved later; enabling it is a deliberate decision to let that client sign in to any Default account's site. Keep banking, email, administrator and other high-impact accounts Sensitive. The group is native-only metadata; changing it to Sensitive, removing the account or locking the vault withdraws group access at the next admission, dispatch or result check, but cannot recall a submission already dispatched. Worker sessions must belong to that client and connection. A workspace grant includes the ability to read pages and use already signed-in sessions. Tab ownership controls mutations; it is not a confidentiality boundary between principals deliberately sharing the same workspace. Workers behind a single paired client are trusted as that client.

Workers automatically own tabs they create. Physical page input preserves that ownership and pauses new agent effects on the affected tab for about two seconds after activity settles; held keys/buttons, IME composition and human-triggered JavaScript dialogs keep it paused. Queued mutations are canceled, previous evidence is invalidated, and interrupted continuations cannot revive after idle. A fresh observation is required before new mutations after activity, except tab close and dialog response; neither exception bypasses an active human pause. Already delivered input and website effects cannot be recalled. Use native **Take ownership** when control should remain with the human until explicitly given back.

The activity resource `xenon://control/activity` and `xenon_activity` contain trusted broker status only, filtered to the paired client's connected workers' owned, granted tabs. They expose activity epochs, pause state and advisory deadlines without recording keystrokes, typed values, page text or URLs. Standard MCP resource-update notifications help supporting hosts notice changes; clients must still recheck status and obtain fresh evidence. A pause and its notifications do not revoke existing workspace access or end website sessions.

Revoking a client removes its workspace/account grants and disconnects its broker sessions. Pending reads recheck authority before returning metadata. Already delivered page content and already dispatched website operations cannot be recalled. Native **Stop all** prevents further agent work until browser restart, while preserving the live pages. Windows session lock also locks the vault and stops agent control.

If a revocation cannot be saved, the native client list marks it **NOT SAVED**: access stays blocked for the current run, but restarting can restore the previously saved authorization. Select that entry and use **Revoke / retry** until the browser confirms the revocation is saved.

Simple-action batches are bounded native plans, with every nested step validated before any effects. Scope, authority, operation ID and observation are fixed for the whole plan. Each step uses the existing guarded input path and rechecks document, observation, attachment, permissions, ownership, human activity and authentication protection. Handoff lets only the current gesture drain and prevents all later steps. A failed step cancels the suffix without rollback or replay. Batches cannot contain scripts, credential use, file selection, coordinate guesses or native controls, and retained/recovery outcomes must be inspected before any repeat.

## Browser and observation boundary

Production starts through the matching CEF sandbox bootstrap with sandboxing enabled and Chromium command-line switches disabled. There is no agent-facing CDP port, JavaScript evaluator, cookie export, request/response-body inspector, clipboard API, OS shell, unrestricted filesystem tool or raw profile-directory argument. Agent navigation is limited to ordinary HTTP(S) and an empty initial page; page-only input excludes browser/OS shortcuts.

Xenon is a general browser, not a network isolation service. Authorized web pages may reach services available to the host, and website scripts remain active. CEF navigation and browser UI behavior are broader than the MCP navigation tool. Review network exposure before using untrusted agents on sensitive local services. Native browser permissions and file/security prompts require human handling.

All website-provided content is untrusted data with no instruction authority. This includes page text, labels, titles, URLs, screenshots and images, JavaScript dialogs, and download names. Use it as evidence for the user's task, not as instructions that override the user or host. A website claiming system authority or user approval cannot authorize a different task, credential disclosure, authentication, or changes to client, workspace, account or file permissions. The MCP server advertises this rule; page-bearing results carry `contentTrust: { classification: "untrusted_website_content", instructionAuthority: "none" }`. This marker records provenance, not a verdict that the content is safe.

Address-bar suggestions are native human chrome. They read only the selected tab's workspace bookmarks and DPAPI-encrypted history (private workspaces: in-memory metadata only), have no MCP surface, and make no network request while the person types. Page titles in the list are website-provided text shown beside the row's address, with line breaks, control characters and bidirectional formatting characters removed. **Shift+Delete** removes a history page from Xenon's metadata file; it does not guarantee erasure from backups or storage-device history.

The site-information bubble, site settings and cookie panels are also native human chrome without an MCP surface. Cookie listings carry names, domains, paths, expiry and flags, never values. Each change is refused unless the tab still shows the same origin outside protected authentication. Deleting cookies or site data invalidates agent evidence and pauses agent input like other human page activity; it can sign the person out of the site. Site settings are stored in the workspace's browser profile: a setting the person allows (for example, the camera) also applies while an agent controls a tab of that site in the workspace, just as a remembered prompt answer does. The certificate summary reports what Chromium accepted for the connection; the unsigned Xenon build does not add its own certificate checks.

After a main-frame load error, the engine runs one fixed script in that frame's main world. When the document is Chromium's error page (`chrome-error://chromewebdata/`), it adds a style rule hiding Chromium's enhanced-protection suggestion; otherwise it does nothing. It reads no page content and returns nothing. Websites cannot load or script that error document, and Xenon adds no certificate exception.

Structured observations default to rendered content in the current viewport. Hidden accessibility names, `title`/`alt` attributes and descriptions are omitted; control labels are derived only from rendered visible text. Query and wait operate on the same filtered evidence. This reduces exposure to attacks hidden in metadata or offscreen content, but visible text, dialogs and images can still contain prompt injection. Xenon cannot decide the host's task authority or make an LLM immune to website instructions. The agent host remains responsible for interpreting evidence and approving consequential actions.

The adapter also checks string values in page results and file metadata for unsafe invisible control, bidi and Unicode tag characters. It replaces the entire affected value with `[text withheld: non-rendering characters]` and reports its own `textSafety.withheldValues` count and limitation; it does not silently join the remaining characters. Ordinary Unicode, ZWJ/ZWNJ, variation selectors and tab/newline characters are retained. Screenshot image bytes are separate from this text filter. This bounded filter is not a complete prompt-injection defense.

The filter uses Chromium layout text boxes, paint order, computed styles, contrast and frame visibility. Observations may additionally list viewport control candidates with `visibilityStatus: uncertain`, a reason and screenshot guidance. Candidate labels use independently verified rendered text only; raw AX labels, values and credentials are not exposed. Candidates receive no action reference and are excluded from guarded element revalidation. The human inspector can match candidates by reported position and draw an explicitly approximate amber outline using native geometry. Those diagnostic identities are stored separately from the published agent target map and cannot authorize input. Screenshot-bound coordinate input retains its existing ownership and native hit checks. Known hidden controls and controls in unproven frame embeddings remain excluded. It reports omissions and conservative thresholds in `visibility`, and declines uncertain clipping, overlays, effects and control-bearing Unicode runs. Ordinary sRGB box shadows use conservative paint bounds covering their offsets, blur and spread, clipped by ancestor overflow; inset shadows stay within the element box. CSS brightness darkening from zero to one has bounded paint; text contrast uses conservative foreground/background luminance intervals and applies each element's filter once. Darkened frame embeddings remain withheld because the child snapshot cannot account for those parent effects. Unsupported shadow syntax/colors, transformed shadow ancestry, text shadows and unsupported filters remain potential unbounded blockers. Single `invert()` effects preserve paint bounds while their own rendered content remains withheld. Pure Gaussian blur paint uses three-sigma raster expansion around the union of its source and overflow descendants. Bounded 2D transform norms expand that support conservatively; perspective, unsupported source paint and excessive ancestry remain uncertain. This paint calculation does not admit blurred or transformed text or action geometry. This can omit legitimate content, including small text and some languages or complex layouts; use screenshots when needed. It is not a pixel-by-pixel legibility proof: custom fonts, rendering tricks and visual attacks can still mislead a model. Hidden-content filtering and the untrusted-content rule are separate protections.

Structured observations omit editable values and do not expose protected password node references. Screenshots are withheld when credential fields, protected authentication or an unverified frame make capture unsafe. In-flight observations are rejected when the broker detects physical activity, a concurrent action, ownership change or protected-login transition; a snapshot during the physical pause cannot authorize later input. These are conservative filters, not a complete secret classifier: a page can render private information in ordinary text, labels, canvas or images. Session pages may naturally display the user's identity or account data.

Identity transforms and bounded 2D translations preserve snapshot axes and dimensions and are supported without applying their offsets twice. Axis-aligned unit reflections retain control geometry, but rendered text requires the full element transform chain to finish upright on both axes. LayoutText's copied styles do not apply transforms twice. Reflected clipping and frame embeddings remain withheld; reflected shadow ancestry remains uncertain paint. Rotations, non-unit scaling, skew and perspective remain unsupported. Repeated inline fragments keep their DOM paint ancestry only when computed styles match and fragment overflow is visible. Combined element geometry requires its action center to lie inside a verified fragment; gaps and inconsistent fragments remain withheld. Backdrop-filter output is bounded by the transformed border box, as specified in [Filter Effects 2](https://drafts.fxtf.org/filter-effects-2/#backdrop-filter-operation); it blocks overlapping evidence rather than unrelated pixels. Backdrop effects preserve descendant control geometry, while descendant text remains withheld because backdrop contrast is unproven. Frame embeddings with backdrop effects remain withheld. Separate foreground filters or extending shadows retain their own paint restrictions. Rectangular `clip-path: inset(...)` in pixel or percentage units is supported when the verified region contains the evidence bounds; rounded or arbitrary paths remain unsupported. The human inspector adds aggregate omission counts and up to eight short, untrusted examples each of unsupported transforms and paint effects. Those examples are disabled for agent observations and action revalidation. The details pane shows aggregate visibility diagnostics even when no row is selected.

## Native browsing features

Full screen, site icons, links for other apps, screen sharing, bookmarks and history management, import, Clear browsing data and Settings are native human chrome with no MCP surface.

**Agent help requests.** `xenon_attention` changes broker metadata only: it sends no engine command, changes no ownership and grants nothing. The broker accepts it only from the tab's current owner, at the current generation, with interaction permission, and drops it when that ownership, the worker's attachment or the permission ends. Marking a request seen and dismissing it are native-only calls. The optional reason is agent-authored text, shown attributed to the agent in the ownership chip menu, the status line and, only if the person enabled it, a Windows notification. Native code refuses control characters, line breaks and invisible formatting so it cannot pose as Xenon's own text, and other clients sharing the workspace never receive it. The notification names the tab's site rather than its website-controlled title. A misled or compromised agent can still write misleading words, so the user guide tells people never to enter secrets because a note asks for them. Alerts are limited to one per tab per minute, and notifications are off by default.

**Full screen.** **F11** is a human shell command. A page's fullscreen request resizes the window only for the selected tab the person controls (broker owner `human`); other tabs' pages fill just their tab area. Page full screen ends when another tab is selected or the person no longer controls the tab, and a notice names the site. While an agent is available in the selected tab, the full-screen page keeps a thin ownership-colored outline.

**Site icons** are website images downloaded as favicons, which carry no cookies. They are bounded to 128×128 pixels, shown only in the tab list and cleared when the tab moves to another origin.

**Links for other apps.** Navigations and popups to schemes other than HTTP(S), `javascript:` and installed extensions' pages never load in the tab. A scheme can reach the person only if it is a syntactically valid non-drive scheme outside a fixed denial list (Xenon's own schemes and `file:`, `shell:`, `ms-msdt:`, `search-ms:`, `ms-appinstaller:`, `vbscript:`, `view-source:` and similar handlers that run programs, searches or diagnostics), the URL is at most 2048 bytes, the request comes from the main frame or a user gesture, the tab is not under protected authentication, and either the person controls the tab or their own physical input in it is under 15 seconds old with no agent page action since (the passkey gate's rule). Only the selected tab of a window can ask, one prompt at a time per tab. The non-activating native prompt names the requesting document's origin, the app Windows has registered and the link; nothing opens without **Open app**. The link is percent-escaped as Chromium's `EscapeExternalHandlerValue` does (control characters, spaces, non-ASCII bytes, double quotes, angle brackets, backslashes, carets, backticks, braces and vertical bars) and passed to `ShellExecute` off the UI thread; unregistered schemes open nothing. The receiving app gets the whole link and is outside Xenon's control.

**Screen sharing.** Alloy-hosted pages have no source picker, so `getDisplayMedia` shares every display. A request reaches the native **Website permission request** only from the selected tab under the same person-or-recent-gesture rule, outside protected authentication, and not combined with camera or microphone capture; agent-caused and background requests are refused with `NotAllowedError`. The prompt states that the whole screen, including other apps and notifications, is shared. While a tab may be capturing (from the person's approval until Chromium reports that its last video stream ended) agent screenshots of that tab fail with `screen_sharing`, since the page can display the captured screen; text observations remain available. Xenon cannot end a capture on its own; reloading the page does.

**Default-browser launches.** The installer registers a per-user `XenonURL` handler for `http` and `https` only, with the command `Xenon.exe --single-argument %1`, so a link is one argument that cannot add switches. Windows lets only the person make Xenon the default. A launch's links must be ordinary HTTP(S) addresses without credentials or control characters, at most eight per launch, and open as new Personal tabs the person owns. With CEF command-line arguments disabled, Chromium's relaunch notice carries no links, so a second launch for the same data folder hands its links to the running browser through a message-only window named from that folder; the receiver accepts only those same web links. Any program the person runs could already start Xenon with a web link, so this adds no capability.

**Bookmarks, history and import.** Folders, renames, moves and per-visit deletion change the workspace's DPAPI-encrypted metadata only. Import reads the `Bookmarks` and `History` files of a Chromium-family profile the person selects (found from each browser's `Local State` profile names) or a bookmark HTML file of at most 32 MiB; it never reads passwords, cookies or other profile data. History is first copied, with sharing that tolerates the browser holding it open, into a private file under Xenon's data folder, read, then deleted; that copy is plaintext SQLite while it exists. Imported titles and folder names lose control and bidirectional formatting characters, only HTTP(S) URLs are kept, and counts and depth are bounded.

**Clear browsing data** deletes the workspace's history and cookies for the chosen range, and for all time the stored data of origins in its history and open tabs and the HTTP cache. Like deleting one site's data, it pauses agent input in every tab of the workspace and invalidates their evidence. Origins absent from history and open tabs keep their stored data.

## Vault storage and use

The native vault stores a versioned username/password payload encrypted with Windows DPAPI for the current user in SQLite. Account IDs, normalized HTTPS origins and human labels are metadata stored without that encryption; choose labels accordingly. Usernames are not indexed as plaintext. Database files have owner-only ACLs; SQLite uses secure deletion and memory temporary storage. Encryption does not guarantee erasure from backups, Windows paging, crash dumps or storage-device history.

The native move-only secret container wipes its plaintext memory when released. Authentication necessarily creates temporary copies inside Chromium and the internal protocol; those copies are not guaranteed to be immediately erased. No vault API returns a username/password through MCP. `xenon_accounts` returns only account ID, exact origin and human label, filtered by native grants. Account addition, removal, import and grants are native user actions.

At agent login dispatch, the broker derives the allowed origin from the persisted grant, overwriting any claimed origin. The engine revalidates the current top-level HTTPS origin before decrypting and before injecting credentials. It checks the form action's origin, requires a POST form with editable credential fields, rejects ambiguous forms, uses a fixed internal function in an isolated world and pauses detailed page evidence while authentication is protected. Submission uses the single visible actionable native submit button when present, preserving its name/value. Multiple visible submitters are refused; form and button action/method/target overrides must retain the exact HTTPS origin, POST method and current browsing context. The bound fields and destination are rechecked after input/change handlers. GET forms are refused before filling so credentials cannot be placed in a URL by ordinary form submission. Browser validation can leave credentials filled with `submitted: false`; a requested submission does not prove sign-in. The bounded username-first flow stays on the granted origin; cross-origin authentication requires a separately authorized human flow.

The destination site must receive the credentials to authenticate. A malicious, compromised or misleadingly granted site can read, transmit or reflect them; hiding vault plaintext from MCP is not protection from the credential recipient. Redirected pages or post-login pages may expose private information as ordinary page content. The native user must verify the exact origin and whether it is appropriate to grant the client access. Xenon does not claim universal prevention of secret exfiltration by hostile websites.

MFA, passkeys, recovery codes, CAPTCHA, embedded cross-origin login widgets and unusual forms are not automated credential capabilities. Protected state can require explicit native **Resume after login** after the human confirms login is complete and no secret is visible. Navigation to a subsequent document can end protection after the login transaction has settled.

Passkeys use Chromium's WebAuthn implementation and the Windows authenticator (Windows Hello, a security key or a phone); Xenon stores no passkey material and returns none through MCP. A fixed main-world wrapper in every frame asks the native gate before forwarding a `publicKey` request to `navigator.credentials.create` or `get`. Tabs the human controls are unchanged. In any other tab, a request is forwarded only within 15 seconds of the human's own physical click or key press in that tab, with no agent page action since; passkey autofill (`mediation: "conditional"`) is refused there because it has no gesture of its own. A refused request rejects with `NotAllowedError` before Windows is asked, and the tab reports `passkeyNeedsHuman` until it navigates. A forwarded ceremony pauses agent input like a page dialog until the page reports that it settled, for at most 10 minutes. Without an answer from the native gate within 10 seconds the wrapper refuses the request.

Tabs that Xenon opens at a website load it only after the main frame's wrapper is installed, and auto-attached cross-origin frames stay paused until theirs is. A popup opened by a page (`window.open`, target links) is created and navigated by Chromium itself, so its first document can run script before its wrapper is installed; later documents in the popup are covered. The wrapper runs in the page's own JavaScript world and its control messages are bounded and validated natively, but a page can still bypass it for its own origin, for example by tampering before installation in such a popup. WebAuthn binds every credential to its relying party, so a bypass cannot use passkeys for another site. Passkey requests made through other browser APIs, such as payment confirmation, are not wrapped.

### Human saved-account autofill

The native account list can appear about 150 ms after qualified physical page input releases and leaves an eligible login field focused. As in Chromium, each left click that leaves an eligible field focused can show it again; keyboard input alone shows it at most once per document. The human can also click the toolbar key or select a tab in Controls and click **Fill selected login tab**. The list is a non-activating native popup placed under the field from a viewport rectangle the fixed inspection returns; that rectangle is the only page-derived geometry it uses, and pages cannot click, read or move it. Clicking an account row (or **Enter** on a row highlighted with the arrow keys) is the explicit native selection and confirmation. Clicks within 500 ms of the list appearing are ignored, so a click aimed at the page cannot pick an account. While the list is open, native UI consumes only arrow, **Enter** and **Escape** key-downs headed to its source window; other input closes it and reaches the page. Each row shows which paired clients hold a grant for that account in the offer's workspace; this is broker metadata and does not grant access. Fixed inspection may run during the two-second agent cooldown, but held input, dialogs, new input, navigation and vault lock still block or invalidate it; agent effects remain paused. The list shows account labels for the exact HTTPS origin; only an explicit native choice uses an account. Human use requires no agent account grant and creates none. There is no MCP endpoint for requesting, accepting or inspecting these offers.

Inspection retains the exact top-level document, form association and input nodes in an isolated renderer object. A two-field conventional form may omit autocomplete attributes; username-only and password-only phases require explicit `autocomplete="username"` and `autocomplete="current-password"`, respectively. A unique explicitly marked username is preferred over unrelated text fields; duplicate marked usernames are refused. Telephone usernames and text inputs explicitly marked `current-password` are supported. An associated form must post to its own HTTPS origin and current browsing context. Inputs outside any form may instead form one synthetic group, requiring explicit username/current-password semantics for every selected credential field. This exception applies only to human-confirmed, fill-only use; actual GET forms remain refused. Ambiguous, covered, disabled, read-only, OTP and new-password fields are refused. Confirmation revalidates the original nodes, form action or null association, field semantics and values; changed human input, a different typed username or a nonempty password is not overwritten. Filling emits ordinary input/change events but does not submit or advance the form. Website handlers can react to those events. Success is reported only when the original fields still have the same document/form association and requested values afterward; it is not evidence of authentication.

Before decryption, the native transaction seals page evidence, pauses agent effects and cancels queued work without changing the tab's owner or generation. It waits for already dispatched finite actions to finish their balancing releases. A native-only continuation guard checks document/activity identity, origin, lock, cancellation and workspace state; it bypasses only the transaction's own pause, not these checks. Lock cancellation advances a generation that unlocking cannot revive. Offers are one-shot, expire after two minutes and are limited to 64; navigation, new page input, agent mutation, dismissal, closure or lock invalidates them. Existing authentication protection and transient-memory limits still apply. The native picker and real-site human autofill remain manual acceptance work as described in [testing](TESTING.md).

### Human login Save/Update prompts

Xenon can offer to save a human-typed login from a top-level HTTPS page with one current-password field, in a form or among the page's controls outside any form. A fixed isolated-world monitor identifies the login; native checks require recent physical password-edit provenance and matching document, frame and origin. A conventional POST to the same origin and browsing context is offered at submission. Script-driven sign-in (**Enter**, a button press in the login's scope, or a form submission the page cancels to send it from script) is held as a deferred candidate and offered only after the page navigates or the submitted password field leaves the page; it expires after 30 seconds otherwise. Reveal, back, cancel, help, forgot and sign-up buttons and toggles are not attempts. The account comes from one editable username or email field, one non-editable username/email field that a multi-step page repeats, or the account typed with physical input on an earlier username-only step of the same origin and tab within ten minutes. Xenon keeps that typed account in native memory only; agent mutation, native fill, workspace removal, tab closure and Windows lock clear it. A password-only form with no known account is ignored for an origin that already has saved accounts. Private workspaces, agent-filled logins, browser-handled GET or cross-origin submissions, ambiguous fields, new-password/OTP forms and submitter overrides do not qualify. Embedded cross-origin and unusual forms require manual handling; **Save account** and CSV import remain available. A supported password submission may be followed by human-completed MFA.

The submitted credential is temporarily retained as a current-user DPAPI-encrypted native memory candidate, not a saved account. There are at most 64 candidates, each expiring after ten minutes; they do not survive process exit. The engine permits an offer after the qualifying submission (for script-driven sign-in, after navigation or field removal) and physical input settles. This is an offer to save an attempted login, not evidence of successful authentication. An incorrect password can also produce an offer; the native prompt tells the human to save only if the password is correct.

The modeless native bubble, anchored under the browser's toolbar key, displays the exact credential-entry HTTPS origin and a masked username; it never displays a password. HTTPS redirects to an identity provider's MFA service or a destination application, and ordinary subsequent MFA input, do not rebind or discard that encrypted candidate. Only an explicit native **Save** or **Update** confirms storage for the original login origin. A page or MCP client cannot list or accept pending candidates, operate this prompt, or grant itself account access. Saving creates no automatic agent grants. **Not now**, prompt/source-tab closure, non-HTTPS navigation, agent mutation, new qualifying password editing, lock, expiry and shutdown discard the offer. Windows lock also clears capture provenance so unlocking cannot revive an old offer. Unchanged credentials produce no prompt; newer submissions supersede older candidates, and stale confirmations cannot overwrite subsequently changed accounts.

The monitor necessarily reads the site's submitted values and briefly passes plaintext through Chromium and the internal native callback before encryption. These transient copies have the same memory-erasure limits as protected sign-in; they are not sent through MCP, persisted as pending plaintext or logged. A hostile site already receives the entered credentials and can alter its forms or submitted values. Explicit native confirmation is always required; neither website error text nor a claimed success authorizes saving. Renderer-monitor, native-policy and vault tests do not substitute for the pending end-to-end human prompt checks listed in [testing](TESTING.md).

## Extensions

The human toolbar panel reads bounded extension metadata through fixed Chromium-owned WebUI API calls in never-shown, non-activating views of the exact verified workspace context. Native engine permission checks add current-tab access, including temporary `activeTab` access. It reads no website DOM and exposes no script/debugging endpoint to MCP. A changed source URL, document epoch, workspace or lifecycle cancels delivery. Private tabs return no extension metadata. Hidden query browsers and their parent windows close before results are delivered, context release or CEF shutdown.

The pinned engine action patch exports versioned native C entry points, not a renderer/MCP bridge. Native toolbar invocation rechecks the selected live tab, exact workspace context/cache path, document epoch, foreground owner, private/removed/shutdown state and protected interactions immediately before effects. Chromium resolves the enabled extension's current action and popup URL. `ExtensionActionRunner` applies the ordinary human-click permission grant or click event; a genuine `kExtensionPopup` host belongs to that tab's profile. Existing Chromium permission scrubbing remains in `tabs.get/query` results for explicitly registered non-private Alloy tabs. Hidden management/query windows do not become browsing tabs in that list. Tab selection, navigation, protected interactions, closure and shutdown dismiss the popup. No website navigation, grant or ownership handoff is synthesized to create a Chrome tab.

Extension-requested `chrome.action.openPopup()` and side-panel API routes use a versioned native guard on the CEF UI thread to recheck the live source, selected tab, exact profile, authentication/protection, private/removal/shutdown state and foreground enabled owner. They reject unknown windows and profiles. Programmatic popup opening never invokes the human action runner or grants `activeTab`, and refuses to displace another popup. The promise completes after the host's first load or fails on closure/timeout. Side-panel opening retains Chromium's API user-gesture check and extension-origin/declared options; native panel controls do not synthesize that gesture for extension scripts. Side-panel hosts use `kExtensionSidePanel`, remain outside broker/evidence inventories, and cannot cross workspace profiles. Protected interactions and private selection retire extension surfaces. Native geometry notifications contain no pointers, URLs, permission grants or executable content; the shell reads its selected tab's engine state before reserving space.

Pin changes use Chromium's profile preferences and respect forced pins. Site choices use Chromium's permission model and may only select access the extension is allowed to request. The native site switch enables Chromium's `ExtensionsMenuAccessControl` behavior; blocking is enforced for content scripts, not merely the panel. Unblocking preserves each extension's access choices. Native removal and reload require human confirmation, followed by another document/lifecycle check. Permission changes report dispatch and a reload hint; they do not claim that existing injected effects were undone. Installation retains Chromium's package verification and native permission prompt.

Extensions are a human-only native capability. MCP and the broker cannot list, add, enable, open or remove them. The normal manager is Chromium's own `chrome://extensions/` WebUI in an embedded Chrome-style content view inside Xenon, bound to the verified persistent request context of the selected workspace. The exact HTTPS Chrome Web Store origin uses Chromium's native Store APIs, package verification and install-permission dialogs. New Store extensions are profile-specific and use Chromium's lifecycle. Private contexts cannot open this manager. Xenon does not review or sandbox extensions beyond Chromium's extension model.

The native address bar displays this WebUI as `xenon://extensions/` and accepts that exact manager alias, including its paths and query parameters. The underlying WebUI origin and Chromium API bindings remain unchanged. Website URLs, including the Chrome Web Store, are never rebranded. The alias is not accepted by page-navigation policy or MCP and does not authorize other privileged browser pages.

Fixed native-owned presentation code runs only in the manager's main `chrome://extensions/` frame, after native workspace/lifecycle checks. It hides Chromium product artwork inside the manager's toolbar/drawer and the sidebar's Store artwork. It makes existing links to the exact HTTPS Store origins target the current management view, rather than a blocked new window. It does not run on the Store or extension pages, add an install button or native bridge, accept script/data from MCP, change permissions, or bypass Chromium's package/installation confirmation.

Management views have their own native inventory, outside broker tabs, snapshots and session recovery. Native creation verifies the workspace context and cache path and refuses removed, private or shutting-down workspaces. A human-controlled ordinary Store navigation may enter this tab; an agent-owned tab cannot acquire it through navigation. There is no injected Store button, model-supplied script, renderer-to-native install bridge, raw debugging endpoint or additional unsafe-extension-debugging switch. Top-level navigation is restricted to the exact extension-manager WebUI, current/legacy HTTPS Store routes and well-formed extension origins, with Chromium enforcing extension-origin access within the profile. After an admitted Store navigation, the same human-only view may follow exact `https://accounts.google.com/` account-service redirects and return to the Store. Opening the manager or an extension page revokes that account-route allowance; an account URL alone cannot open the management view. Other hosts, HTTP, credentials, explicit ports and lookalikes remain rejected. Account pages retain their real address, receive no manager presentation script, and remain outside MCP/broker observations and input. General browser commands and unrelated website permission prompts are blocked. Chromium retains its native package download and installation handling. Chromium-created auxiliary post-install browsers cannot navigate or change the visible manager state, have their native show requests suppressed, and remain outside both visible tab metadata and MCP. Their rejection waits one UI queue turn before Chromium schedules its own close, preserving the queued completion callback; this changes lifecycle order, not installation approval or verification. Workspace removal closes management and auxiliary browsers before releasing the context, and browser shutdown waits for both to close before quitting CEF. Blank-startup preferences are restored immediately after synchronous manager creation.

Legacy copied extensions remain a separate compatibility facility. Its native picker copies a chosen unpacked Manifest V3 folder into Xenon's data directory, refusing links, reparse points, oversize trees and folders inside the data directory. Those enabled copies still load into every persistent workspace profile at the next start; private workspaces do not load them by default. Existing copies and extension profile data are not silently migrated, replaced or deleted by the new manager.

Legacy **Install from Chrome Web Store link** is also native-only. The pasted link supplies only a validated 32-character extension ID from the exact HTTPS `chromewebstore.google.com/detail/` route; it is never fetched as an arbitrary URL. WinHTTP uses ordinary TLS verification, no browser cookies or automatic authentication, fixed Google update/CRX routes on `clients2.google.com` and `clients2.googleusercontent.com`, at most five redirects, a 120-second request budget and a 128 MiB byte limit. CRX3 verification binds the requested ID to the signed header and developer public key, verifies every RSA-PKCS1-SHA256 or P-256 ECDSA proof over the exact signed header and ZIP bytes, and requires Chromium's pinned production Web Store publisher key hash. Chromium's test publisher key is not accepted. A valid signature establishes package integrity and key identity, not that the extension is trustworthy or compatible.

The legacy importer's ZIP inspection rejects absolute/traversing paths, Windows device names, alternate streams, links, duplicate case-insensitive paths, overlapping entries, encryption and ZIP64. File count includes implied directories; compressed and expanded bytes are bounded separately. CEF decompresses the verified in-memory archive, with exact size and CRC checks. The worker produces an immutable package; no files or registry records are written before the native human confirmation. The scrollable review includes required and optional permissions, host access, content scripts and the full manifest with escaped untrusted strings. Installation writes that exact tree into a managed staging directory and inserts the verified public key into `manifest.json`, rejecting an existing mismatched key, so unpacked loading retains the verified extension ID. Cancel, close, session lock and shutdown cancel the pending package; shutdown joins the worker before CEF stops. Legacy copies do not update automatically and have no Web Store page bridge; the embedded Chrome-style view instead uses Chromium's Store installation handling.

An installed extension runs with the Chromium permissions it declares. On the sites it can access it can read and change page content, observe and alter what the human and agents type, including credentials entered by Xenon's native fill or agent sign-in, read or alter cookies and requests within its permissions, and change what agents observe. Workspace sharing, client capabilities and account grants do not limit an extension. Content an extension injects into a page is website content to agents and carries the same untrusted-content marker. Native Chrome-style extension pages use Chromium's profile/origin enforcement; ordinary Alloy tabs retain the legacy loaded-ID allowlist. Agent observation, screenshots and input refuse non-web pages, and agent navigation accepts only HTTP(S). Install only extensions you trust, and remove an extension if its publisher or behavior becomes untrustworthy. Legacy removal does not explicitly erase extension profile data; Chromium's own removal flow controls the data of profile-installed extensions.

## Tab movement and workspace cleanup

Moving a tab between Xenon windows reparents its native host and does not change the page, request context, owner, generation, pause or evidence. Moving a tab to another workspace cannot carry a live page across profiles; it reopens the address in the target profile as a new human-owned tab. The broker refuses this while any member of the tab's control group has an agent owner (connected or resumable), a pending handoff or accepted input, and for private workspaces and protected authentication. It rechecks before closing the original, so an agent that takes control meanwhile keeps its tab. The reopened address can reveal the URL to the target workspace's clients, and the target site sees that workspace's cookies; this is the human's decision.

Native **Close all tabs** cancels and refuses queued agent mutations for the tabs being closed before any closure. The engine closes them only after accepted finite input and guarded gestures settle. Agents receive `TAB_CLOSED`/`TAB_CLOSING` outcomes; outcomes of already dispatched actions remain journaled. Grants, the workspace profile and saved accounts are unchanged.

## Workspace removal

Removal is a confirmed native action, with Personal protected and no MCP removal tool. A durable, permanent workspace tombstone blocks new access before closure. Existing finite input and tab creation drain; queued mutations are canceled without replay. The workspace's client/account grants are removed, and file grants are revoked as closure completes. Tabs close and outstanding downloads are canceled. The global credential vault, downloaded files and source upload files are retained; removing a workspace does not delete a shared saved account.

Persistent profile deletion is deferred until a later launch, after CEF has acquired the user-data root's single-instance ownership and before the removed workspace can open. Cleanup is bounded, checks the expected hashed profile path, and refuses reparse points and multiply linked files. A retained cursor rotates retries so one blocked workspace does not indefinitely prevent attempts on later entries. Locked, refused or oversized trees can remain on disk; tombstones continue denying their use. This is profile cleanup, not guaranteed forensic erasure or remote account logout.

## Password import

Import supports the exported CSV formats used by Chrome, Edge and Firefox, including UTF-8 BOMs and quoted multiline fields. It accepts supported HTTPS logins, shows a preview with masked usernames and no passwords, and requires native approval. A content digest binds the committed import to the previewed file. Conflicting saved passwords require an explicit replace-or-skip decision. Locked vault operations fail.

The export remains a plaintext file on disk. Xenon does not delete it automatically; remove it once import is complete. Selected import sources are denied as upload sources by final path and file identity, including after rename/restart. That safeguard does not secure unrelated copies, backups or applications that can already read the export. Direct extraction or decryption of another browser's saved passwords and full browser-profile import are not provided; import from another profile reads only its bookmarks and history (see [native browsing features](#native-browsing-features)).

## Files and downloads

Upload grants are selected natively and bind opaque handles to one workspace. The human can approve a regular file or a folder. Folder listing is bounded to at most 1,000 returned files, 5,000 traversed entries and depth eight, reports truncation, and returns relative names and opaque file IDs rather than absolute paths or file contents. A folder grant intentionally permits eligible files found later within that folder; select an individual file when that scope is too broad. Grants persist and can be revoked natively.

Pagination/filtering applies the same native resource selection before the page cap. Opaque cursors bind worker/client/workspace, file scopes, folder and query, expire after two minutes, and retain at most 32 process-local discovery snapshots. Each page reopens candidates and rechecks identity, protected paths and current grants; revocation invalidates cursors. Continuation does not expand authorization. `truncated` reports either a remaining page or an incomplete bounded scan; `scanIncomplete` and nullable `nextCursor` distinguish those cases.

Direct file discovery accepts a `relativePath` of at most 500 UTF-8 bytes under an existing approved `folderId`, without query or cursor. It opens only that candidate, avoiding recursive scan limits, and applies the same scope, selected-resource, protected-file, link, ancestor-lock, final-path and identity validation. Rooted paths, traversal, streams and ambiguous components are rejected natively before opening the candidate. The result is an opaque upload handle, never file contents or a new folder permission.

The file boundary rejects profile/vault/policy/import-source files, reparse paths, symlinks, hard-linked files, traversal, alternate data streams, UNC and device paths. It resolves the final path and retains file/ancestor handles to prevent replacement during the upload transaction. Folder listing applies the same protected-path rules; a grant does not override them.

An upload targets either an observed visible file input or an observed visible upload entry that opens a chooser in its own frame. The entry is activated once with a fixed element click, including a verified StaticText reference for custom entries without button semantics. Text targeting uses its exact single rendered range, rechecks its visibility and hit area, and never expands to a parent container's bounds. Disabled/inert ancestors and fragmented text are refused. Chromium's intercepted chooser event identifies the exact input; its session, frame and source document must match before assignment, even when the input itself is hidden. This grants no hidden-DOM search or OS-picker capability. Directory uploads, File System Access API pickers and different-frame delegation are unsupported. Native file permission is revalidated before selection, and ownership/activity/document/authentication checks continue through asynchronous steps. Interrupted transactions disable interception without clearing inputs or injecting a late cancel into a new owner's page.

Selecting a file gives the destination website access to that file through normal browser behavior. Xenon does not infer the website's upload endpoint or prevent an authorized destination from transmitting the selected contents. A button can also cause unrelated page effects before opening its chooser. Upload responses therefore distinguish activation from selection; unknown outcomes require inspection rather than automatic retries. A successful selection is not proof of server-side upload completion.

Known pairing-configuration names and JSON objects containing a client ID and pairing token are excluded at grant, list and upload resolution, including edits to an already granted file. The bounded content probe also denies JSON objects larger than 1 MiB and larger whitespace-only files, so a token cannot be hidden beyond its scan window. This conservative limitation can exclude otherwise benign large JSON uploads.

Downloads receive sanitized unique names in managed workspace storage. They are not automatically opened, and the MCP API exposes download metadata rather than arbitrary local file access. Downloaded files can still be malicious; Xenon does not include a malware-analysis service. Individual upload grants are not permission to inspect an entire directory.

## Retention and diagnostics

The default data directory is `%LOCALAPPDATA%\Xenon Browser`. Workspace profile data and the vault persist until removed by the user. Native startup accepts a user-selected data directory; it is not available through MCP. Pairing configuration lives at the path selected during pairing. Native session recovery stores eligible workspace/tab IDs and URLs in a current-user DPAPI-encrypted index. Recovery reloads pages only after the human requests it and restores human ownership; it does not restore a live renderer or replay MCP actions.

Ordinary startup opens a blank tab while persistent workspaces retain cookies, including session cookies. Closing Xenon is therefore not a global website sign-out. A site's logout may also leave its identity provider's SSO session active. Use a fresh workspace for a separate sign-in session; doing so does not revoke or delete the original workspace's session. Private workspaces do not persist their cookies. Saved-password encryption and website session lifetime are separate concerns.

Native private workspaces use off-the-record request contexts and are excluded from persisted workspace grants and the session recovery index. They cannot be shared with MCP clients in this release. Private browsing is not anonymity from websites, the network, the operating system or local malware; downloaded files and information explicitly saved outside the private profile may remain.

The recovery journal persists only IDs, principal/tab association, state and dispatch status. It does not persist tool arguments, page evidence, results or credential content. At most 4,096 operation records are retained. In-memory operation results are process-local and may contain ordinary page data. Chromium profiles contain normal browsing/site data independently of the broker journal. Default operation does not log raw protocol or credential data, suppresses page-console forwarding, and requests disabled CEF/Chromium logging. Chromium may still emit startup diagnostics. Test fixtures and integration outputs are synthetic and must not be repurposed to record real secrets.

The adapter's optional `serve --evidence-dir` explicitly records schema-accepted public tool arguments and exact MCP replies in a new current-user private directory, with received permitted PNGs. It is off by default, bounded to 256 MiB per run, and does not capture pairing, tokens/configuration, native credential traffic, schema-rejected inputs or background resource polls. Ordinary task arguments and permitted website results can contain private information; these exports must remain outside source control. A failed request write prevents dispatch; a failed result write preserves the operation's received outcome and reports export failure separately. No export triggers retries. Native recovery remains metadata-only.

Terminal journal writes are asynchronous. A crash may leave an operation uncertain even when it completed. Recovery does not replay it. Retention is bounded, so no caller should assume indefinite exactly-once execution or treat an unknown operation as proof that nothing happened.

## Maintenance and reporting

The native Updates window is unavailable through MCP or page scripts. Its WinHTTP requests use no browser profile, cookies or pairing credentials. It only selects versioned Windows installer assets from `Xero-05/xenon-browser`, requires GitHub's SHA-256 asset digest and exact byte count, bounds response sizes and time, and restricts HTTPS redirects to GitHub's release infrastructure. The installer is downloaded into private staging and reverified before launch. Failed or cancelled partial downloads cannot become runnable updates. Same-user malware remains outside the protection boundary.

This release is unsigned. HTTPS and a checksum from the same GitHub account detect transfer corruption and unexpected bytes; they do not protect against a compromised repository, GitHub account or build pipeline. They are not Authenticode publisher authentication. A future signed channel must verify its expected publisher and timestamp before execution; merely adding a certificate to setup does not establish that policy.

Updates require explicit native human actions. **Install and exit** requires confirmation before normal browser shutdown. The updater reverifies its private staged image, creates that exact image suspended while holding its file and ancestor handles, and starts it only after CEF, the broker and this instance's running marker have closed. Discarding a prepared update cancels only its own still-suspended setup process. Setup refuses installation while any other browser instance is running; no unrelated process or external MCP host is terminated. The installer replaces application files in the per-user program directory and retains the separate profile/vault and pairing configuration. Restart is a normal restart, not a seamless live-tab handoff. The installer rejects a version older than its recorded installed version. There is no service, scheduled task, arbitrary update URL or forced unattended installation.

While Xenon runs, it checks release metadata about 20 seconds after start and then every six hours, unless **Check for updates automatically** is turned off in Updates. This is the same fixed, unauthenticated metadata request as a manual check, so GitHub sees the request's address and timing. It never downloads or installs anything; a newer release only adds a blue dot to Controls, a menu entry and a Controls button label. The unshipped `XenonAuthTest` build never checks automatically.

Security depends on shipping a maintained, matching Chromium/CEF distribution. Dependency selection and release publication remain maintainer-controlled. Follow the [CEF update and test procedure](BUILD.md) before releases. Do not add `--no-sandbox`, certificate-error bypasses, exposed debugging ports or credential logging to make a site work. The integration-only certificate fixture is compiled into a separate test build and is not a production bypass.

Use [GitHub private vulnerability reporting](https://github.com/Xero-05/xenon-browser/security/advisories/new) for suspected vulnerabilities. See the repository's [reporting policy](../SECURITY.md) for useful reproduction details and the maintainer response policy. Do not post passwords, pairing tokens, sensitive page captures or a working secret-exfiltration payload in a public issue. No audit, security response SLA or supported-version commitment is implied by this release.
