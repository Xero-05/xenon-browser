# Security boundary and alpha limitations

Client policy is enforced natively as a ceiling over each workspace's client-specific permissions. New pairings are read-only and cannot create automatic workspaces until configured in native Controls. Interaction, upload, download and saved-account capabilities are checked at admission, dispatch and asynchronous continuation; late results are withheld after permission revocation. Client resources may be inherited live, with workspace restrictions narrowing that selection. Account inheritance preserves exact HTTPS-origin grants, and inherited files retain final-path and file-identity checks. CEF download callbacks also gate downloads caused indirectly by agent-owned pages. Native configuration is unavailable through MCP.

Xenon is an unsigned, early Windows alpha. It separates MCP authorization, browser profiles and credential use, but it has not received an independent security audit. Its purpose is to prevent routine model/tool access to vault plaintext and to make browser authority explicit. It does not defend a Windows account from malware already running as that account, an administrator, a debugger or a compromised Chromium/CEF runtime.

## Local client authority

The browser serves a Windows named pipe with a protected current-user SID ACL and `PIPE_REJECT_REMOTE_CLIENTS`. The first listener claims the pipe name exclusively to detect another owner. A connected process must also pair through the native UI or authenticate with a previously issued token. A forged `clientId` inside page parameters is ignored; the authenticated connection establishes identity.

Private directories inherit current-user access to their descendants. This preserves browser access when Chromium adds sandbox capability permissions to its network-storage directories; it grants no additional user access. File and pipe ACLs remain non-inheritable.

The adapter stores the token in a separately protected configuration file. The broker stores its SHA-256 hash, not the token. Native-generated identifiers and tokens use the Windows cryptographic RNG. Configuration and browser data must remain private to their Windows user. Processes running as that same user can potentially access those files or the process itself; the pairing token is not a sandbox against local malware.

Authorization is per paired client and workspace, with separate account grants tied to client, workspace, account and exact HTTPS origin. Worker sessions must belong to that client and connection. A workspace grant includes the ability to read pages and use already signed-in sessions. Tab ownership controls mutations; it is not a confidentiality boundary between principals deliberately sharing the same workspace. Workers behind a single paired client are trusted as that client.

Workers automatically own tabs they create. Physical page input preserves that ownership and pauses new agent effects on the affected tab for about two seconds after activity settles; held keys/buttons, IME composition and human-triggered JavaScript dialogs keep it paused. Queued mutations are canceled, previous evidence is invalidated, and interrupted continuations cannot revive after idle. A fresh observation is required before new mutations after activity, except tab close and dialog response; neither exception bypasses an active human pause. Already delivered input and website effects cannot be recalled. Use native **Take ownership** when control should remain with the human until explicitly given back.

The activity resource `xenon://control/activity` and `xenon_activity` contain trusted broker status only, filtered to the paired client's connected workers' owned, granted tabs. They expose activity epochs, pause state and advisory deadlines without recording keystrokes, typed values, page text or URLs. Standard MCP resource-update notifications help supporting hosts notice changes; clients must still recheck status and obtain fresh evidence. A pause and its notifications do not revoke existing workspace access or end website sessions.

Revoking a client removes its workspace/account grants and disconnects its broker sessions. Pending reads recheck authority before returning metadata. Already delivered page content and already dispatched website operations cannot be recalled. Native **Stop all** prevents further agent work until browser restart, while preserving the live pages. Windows session lock also locks the vault and stops agent control.

If a revocation cannot be saved, the native client list marks it **NOT SAVED**: access stays blocked for the current run, but restarting can restore the previously saved authorization. Select that entry and use **Revoke / retry** until the browser confirms the revocation is saved.

Simple-action batches are bounded native plans, with every nested step validated before any effects. Scope, authority, operation ID and observation are fixed for the whole plan. Each step uses the existing guarded input path and rechecks document, observation, attachment, permissions, ownership, human activity and authentication protection. Handoff lets only the current gesture drain and prevents all later steps. A failed step cancels the suffix without rollback or replay. Batches cannot contain scripts, credential use, file selection, coordinate guesses or native controls, and retained/recovery outcomes must be inspected before any repeat.

## Browser and observation boundary

Production starts through the matching CEF sandbox bootstrap with sandboxing enabled and Chromium command-line switches disabled. There is no agent-facing CDP port, JavaScript evaluator, cookie export, request/response-body inspector, clipboard API, OS shell, unrestricted filesystem tool or raw profile-directory argument. Agent navigation is limited to ordinary HTTP(S) and an empty initial page; page-only input excludes browser/OS shortcuts.

Xenon is a general browser, not a network isolation service. Authorized web pages may reach services available to the host, and website scripts remain active. CEF navigation and browser UI behavior are broader than the MCP navigation tool. Review network exposure before using untrusted agents on sensitive local services. Native browser permissions and file/security prompts require human handling.

All website-provided content is untrusted data with no instruction authority. This includes page text, labels, titles, URLs, screenshots and images, JavaScript dialogs, and download names. Use it as evidence for the user's task, not as instructions that override the user or host. A website claiming system authority or user approval cannot authorize a different task, credential disclosure, authentication, or changes to client, workspace, account or file permissions. The MCP server advertises this rule; page-bearing results carry `contentTrust: { classification: "untrusted_website_content", instructionAuthority: "none" }`. This marker records provenance, not a verdict that the content is safe.

Structured observations default to rendered content in the current viewport. Hidden accessibility names, `title`/`alt` attributes and descriptions are omitted; control labels are derived only from rendered visible text. Query and wait operate on the same filtered evidence. This reduces exposure to attacks hidden in metadata or offscreen content, but visible text, dialogs and images can still contain prompt injection. Xenon cannot decide the host's task authority or make an LLM immune to website instructions. The agent host remains responsible for interpreting evidence and approving consequential actions.

The adapter also checks string values in page results and file metadata for unsafe invisible control, bidi and Unicode tag characters. It replaces the entire affected value with `[text withheld: non-rendering characters]` and reports its own `textSafety.withheldValues` count and limitation; it does not silently join the remaining characters. Ordinary Unicode, ZWJ/ZWNJ, variation selectors and tab/newline characters are retained. Screenshot image bytes are separate from this text filter. This bounded filter is not a complete prompt-injection defense.

The filter uses Chromium layout text boxes, paint order, computed styles, contrast and frame visibility. It reports omissions and conservative thresholds in `visibility`, and declines uncertain clipping, overlays, effects and control-bearing Unicode runs. Ordinary sRGB box shadows use conservative paint bounds covering their offsets, blur and spread, clipped by ancestor overflow; inset shadows stay within the element box. CSS brightness darkening from zero to one has bounded paint; text contrast uses conservative foreground/background luminance intervals and applies each element's filter once. Darkened frame embeddings remain withheld because the child snapshot cannot account for those parent effects. Unsupported shadow syntax/colors, transformed shadow ancestry, text shadows and other filters remain potential unbounded blockers. This can omit legitimate content, including small text and some languages or complex layouts; use screenshots when needed. It is not a pixel-by-pixel legibility proof: custom fonts, rendering tricks and visual attacks can still mislead a model. Hidden-content filtering and the untrusted-content rule are separate protections.

Structured observations omit editable values and do not expose protected password node references. Screenshots are withheld when credential fields, protected authentication or an unverified frame make capture unsafe. In-flight observations are rejected when the broker detects physical activity, a concurrent action, ownership change or protected-login transition; a snapshot during the physical pause cannot authorize later input. These are conservative filters, not a complete secret classifier: a page can render private information in ordinary text, labels, canvas or images. Session pages may naturally display the user's identity or account data.

## Vault storage and use

The native vault stores a versioned username/password payload encrypted with Windows DPAPI for the current user in SQLite. Account IDs, normalized HTTPS origins and human labels are metadata stored without that encryption; choose labels accordingly. Usernames are not indexed as plaintext. Database files have owner-only ACLs; SQLite uses secure deletion and memory temporary storage. Encryption does not guarantee erasure from backups, Windows paging, crash dumps or storage-device history.

The native move-only secret container wipes its plaintext memory when released. Authentication necessarily creates temporary copies inside Chromium and the internal protocol; those copies are not guaranteed to be immediately erased. No vault API returns a username/password through MCP. `xenon_accounts` returns only account ID, exact origin and human label, filtered by native grants. Account addition, removal, import and grants are native user actions.

At agent login dispatch, the broker derives the allowed origin from the persisted grant, overwriting any claimed origin. The engine revalidates the current top-level HTTPS origin before decrypting and before injecting credentials. It checks the form action's origin, requires a POST form with editable credential fields, rejects ambiguous forms, uses a fixed internal function in an isolated world and pauses detailed page evidence while authentication is protected. Submission uses the single visible actionable native submit button when present, preserving its name/value. Multiple visible submitters are refused; form and button action/method/target overrides must retain the exact HTTPS origin, POST method and current browsing context. The bound fields and destination are rechecked after input/change handlers. GET forms are refused before filling so credentials cannot be placed in a URL by ordinary form submission. Browser validation can leave credentials filled with `submitted: false`; a requested submission does not prove sign-in. The bounded username-first flow stays on the granted origin; cross-origin authentication requires a separately authorized human flow.

The destination site must receive the credentials to authenticate. A malicious, compromised or misleadingly granted site can read, transmit or reflect them; hiding vault plaintext from MCP is not protection from the credential recipient. Redirected pages or post-login pages may expose private information as ordinary page content. The native user must verify the exact origin and whether it is appropriate to grant the client access. Xenon does not claim universal prevention of secret exfiltration by hostile websites.

MFA, passkeys, recovery codes, CAPTCHA, embedded cross-origin login widgets and unusual forms are not automated credential capabilities. Protected state can require explicit native **Resume after login** after the human confirms login is complete and no secret is visible. Navigation to a subsequent document can end protection after the login transaction has settled.

### Human saved-account autofill

The native account picker can appear about 250 ms after qualified physical page input releases and leaves an eligible login field focused. Automatic offers are limited to one per document. The human can also select a tab in Controls and click **Fill saved account…**. Fixed inspection may run during the two-second agent cooldown, but held input, dialogs, new input, navigation and vault lock still block or invalidate it; agent effects remain paused. The picker identifies the exact HTTPS origin and account labels; only an explicit native **Fill** uses the chosen account. Human use requires no agent account grant and creates none. There is no MCP endpoint for requesting, accepting or inspecting these offers.

Inspection retains the exact top-level document, form association and input nodes in an isolated renderer object. A two-field conventional form may omit autocomplete attributes; username-only and password-only phases require explicit `autocomplete="username"` and `autocomplete="current-password"`, respectively. A unique explicitly marked username is preferred over unrelated text fields; duplicate marked usernames are refused. Telephone usernames and text inputs explicitly marked `current-password` are supported. An associated form must post to its own HTTPS origin and current browsing context. Inputs outside any form may instead form one synthetic group, requiring explicit username/current-password semantics for every selected credential field. This exception applies only to human-confirmed, fill-only use; actual GET forms remain refused. Ambiguous, covered, disabled, read-only, OTP and new-password fields are refused. Confirmation revalidates the original nodes, form action or null association, field semantics and values; changed human input, a different typed username or a nonempty password is not overwritten. Filling emits ordinary input/change events but does not submit or advance the form. Website handlers can react to those events. Success is reported only when the original fields still have the same document/form association and requested values afterward; it is not evidence of authentication.

Before decryption, the native transaction seals page evidence, pauses agent effects and cancels queued work without changing the tab's owner or generation. It waits for already dispatched finite actions to finish their balancing releases. A native-only continuation guard checks document/activity identity, origin, lock, cancellation and workspace state; it bypasses only the transaction's own pause, not these checks. Lock cancellation advances a generation that unlocking cannot revive. Offers are one-shot, expire after two minutes and are limited to 64; navigation, new page input, agent mutation, dismissal, closure or lock invalidates them. Existing authentication protection and transient-memory limits still apply. The native picker and real-site human autofill remain manual acceptance work as described in [testing](TESTING.md).

### Human login Save/Update prompts

Xenon can offer to save a human-typed login from a conventional top-level HTTPS form with one editable username and one current password, submitted with POST to the same origin and browsing context. A fixed isolated-world monitor identifies the form; native checks require recent physical password-edit provenance and matching document, frame and origin. Private workspaces, agent-filled logins, GET forms, ambiguous or read-only fields, new-password/OTP forms and submitter overrides do not qualify. Username-first, embedded and unusual forms require manual handling; **Save account** and CSV import remain available. A supported password submission may be followed by human-completed MFA.

The submitted credential is temporarily retained as a current-user DPAPI-encrypted native memory candidate, not a saved account. There are at most 64 candidates, each expiring after ten minutes; they do not survive process exit. The engine permits an offer after the qualifying submission and physical input settles. This is an offer to save an attempted login, not evidence of successful authentication. An incorrect password can also produce an offer; the native prompt tells the human to save only if the password is correct.

The modeless native prompt displays the exact credential-entry HTTPS origin and a masked username; it never displays a password. HTTPS redirects to an identity provider's MFA service or a destination application, and ordinary subsequent MFA input, do not rebind or discard that encrypted candidate. Only an explicit native **Save** or **Update** confirms storage for the original login origin. A page or MCP client cannot list or accept pending candidates, operate this prompt, or grant itself account access. Saving creates no automatic agent grants. **Not now**, prompt/source-tab closure, non-HTTPS navigation, agent mutation, new qualifying password editing, lock, expiry and shutdown discard the offer. Windows lock also clears capture provenance so unlocking cannot revive an old offer. Unchanged credentials produce no prompt; newer submissions supersede older candidates, and stale confirmations cannot overwrite subsequently changed accounts.

The monitor necessarily reads the site's submitted values and briefly passes plaintext through Chromium and the internal native callback before encryption. These transient copies have the same memory-erasure limits as protected sign-in; they are not sent through MCP, persisted as pending plaintext or logged. A hostile site already receives the entered credentials and can alter its forms or submitted values. Explicit native confirmation is always required; neither website error text nor a claimed success authorizes saving. Renderer-monitor, native-policy and vault tests do not substitute for the pending end-to-end human prompt checks listed in [testing](TESTING.md).

## Workspace removal

Removal is a confirmed native action, with Personal protected and no MCP removal tool. A durable, permanent workspace tombstone blocks new access before closure. Existing finite input and tab creation drain; queued mutations are canceled without replay. The workspace's client/account grants are removed, and file grants are revoked as closure completes. Tabs close and outstanding downloads are canceled. The global credential vault, downloaded files and source upload files are retained; removing a workspace does not delete a shared saved account.

Persistent profile deletion is deferred until a later launch, after CEF has acquired the user-data root's single-instance ownership and before the removed workspace can open. Cleanup is bounded, checks the expected hashed profile path, and refuses reparse points and multiply linked files. A retained cursor rotates retries so one blocked workspace does not indefinitely prevent attempts on later entries. Locked, refused or oversized trees can remain on disk; tombstones continue denying their use. This is profile cleanup, not guaranteed forensic erasure or remote account logout.

## Password import

Import supports the exported CSV formats used by Chrome, Edge and Firefox, including UTF-8 BOMs and quoted multiline fields. It accepts supported HTTPS logins, shows a preview with masked usernames and no passwords, and requires native approval. A content digest binds the committed import to the previewed file. Conflicting saved passwords require an explicit replace-or-skip decision. Locked vault operations fail.

The export remains a plaintext file on disk. Xenon does not delete it automatically; remove it once import is complete. Selected import sources are denied as upload sources by final path and file identity, including after rename/restart. That safeguard does not secure unrelated copies, backups or applications that can already read the export. Direct extraction/decryption of another browser's live profile and full browser-profile import are not provided.

## Files and downloads

Upload grants are selected natively and bind opaque handles to one workspace. The human can approve a regular file or a folder. Folder listing is bounded to at most 1,000 returned files, 5,000 traversed entries and depth eight, reports truncation, and returns relative names and opaque file IDs rather than absolute paths or file contents. A folder grant intentionally permits eligible files found later within that folder; select an individual file when that scope is too broad. Grants persist and can be revoked natively.

Pagination/filtering applies the same native resource selection before the page cap. Opaque cursors bind worker/client/workspace, file scopes, folder and query, expire after two minutes, and retain at most 32 process-local discovery snapshots. Each page reopens candidates and rechecks identity, protected paths and current grants; revocation invalidates cursors. Continuation does not expand authorization. `truncated` reports either a remaining page or an incomplete bounded scan; `scanIncomplete` and nullable `nextCursor` distinguish those cases.

The file boundary rejects profile/vault/policy/import-source files, reparse paths, symlinks, hard-linked files, traversal, alternate data streams, UNC and device paths. It resolves the final path and retains file/ancestor handles to prevent replacement during the upload transaction. Folder listing applies the same protected-path rules; a grant does not override them.

An upload targets either an observed visible file input or an observed visible upload entry that opens a chooser in its own frame. The entry is activated once with a fixed element click. Chromium's intercepted chooser event identifies the exact input; its session, frame and source document must match before assignment, even when the input itself is hidden. This grants no hidden-DOM search or OS-picker capability. Directory uploads, File System Access API pickers and different-frame delegation are unsupported. Native file permission is revalidated before selection, and ownership/activity/document/authentication checks continue through asynchronous steps. Interrupted transactions disable interception without clearing inputs or injecting a late cancel into a new owner's page.

Selecting a file gives the destination website access to that file through normal browser behavior. Xenon does not infer the website's upload endpoint or prevent an authorized destination from transmitting the selected contents. A button can also cause unrelated page effects before opening its chooser. Upload responses therefore distinguish activation from selection; unknown outcomes require inspection rather than automatic retries. A successful selection is not proof of server-side upload completion.

Known pairing-configuration names and JSON objects containing a client ID and pairing token are excluded at grant, list and upload resolution, including edits to an already granted file. The bounded content probe also denies JSON objects larger than 1 MiB and larger whitespace-only files, so a token cannot be hidden beyond its scan window. This conservative alpha limitation can exclude otherwise benign large JSON uploads.

Downloads receive sanitized unique names in managed workspace storage. They are not automatically opened, and the MCP API exposes download metadata rather than arbitrary local file access. Downloaded files can still be malicious; Xenon does not include a malware-analysis service. Individual upload grants are not permission to inspect an entire directory.

## Retention and diagnostics

The default data directory is `%LOCALAPPDATA%\Xenon Browser`. Workspace profile data and the vault persist until removed by the user. Native startup accepts a user-selected data directory; it is not available through MCP. Pairing configuration lives at the path selected during pairing. Native session recovery stores eligible workspace/tab IDs and URLs in a current-user DPAPI-encrypted index. Recovery reloads pages only after the human requests it and restores human ownership; it does not restore a live renderer or replay MCP actions.

Ordinary startup opens a blank tab while persistent workspaces retain cookies, including session cookies. Closing Xenon is therefore not a global website sign-out. A site's logout may also leave its identity provider's SSO session active. Use a fresh workspace for a separate sign-in session; doing so does not revoke or delete the original workspace's session. Private workspaces do not persist their cookies. Saved-password encryption and website session lifetime are separate concerns.

Native private workspaces use off-the-record request contexts and are excluded from persisted workspace grants and the session recovery index. They cannot be shared with MCP clients in this alpha. Private browsing is not anonymity from websites, the network, the operating system or local malware; downloaded files and information explicitly saved outside the private profile may remain.

The recovery journal persists only IDs, principal/tab association, state and dispatch status. It does not persist tool arguments, page evidence, results or credential content. At most 4,096 operation records are retained. In-memory operation results are process-local and may contain ordinary page data. Chromium profiles contain normal browsing/site data independently of the broker journal. Default operation does not log raw protocol or credential data, suppresses page-console forwarding, and requests disabled CEF/Chromium logging. Chromium may still emit startup diagnostics. Test fixtures and integration outputs are synthetic and must not be repurposed to record real secrets.

The adapter's optional `serve --evidence-dir` explicitly records schema-accepted public tool arguments and exact MCP replies in a new current-user private directory, with received permitted PNGs. It is off by default, bounded to 256 MiB per run, and does not capture pairing, tokens/configuration, native credential traffic, schema-rejected inputs or background resource polls. Ordinary task arguments and permitted website results can contain private information; these exports must remain outside source control. A failed request write prevents dispatch; a failed result write preserves the operation's received outcome and reports export failure separately. No export triggers retries. Native recovery remains metadata-only.

Terminal journal writes are asynchronous. A crash may leave an operation uncertain even when it completed. Recovery does not replay it. Retention is bounded, so no caller should assume indefinite exactly-once execution or treat an unknown operation as proof that nothing happened.

## Maintenance and reporting

The native Updates window is unavailable through MCP or page scripts. Its WinHTTP requests use no browser profile, cookies or pairing credentials. It only selects versioned Windows installer assets from `Xero-05/xenon-browser`, requires GitHub's SHA-256 asset digest and exact byte count, bounds response sizes and time, and restricts HTTPS redirects to GitHub's release infrastructure. The installer is downloaded into private staging and reverified before launch. Failed or cancelled partial downloads cannot become runnable updates. Same-user malware remains outside the protection boundary.

This alpha is unsigned. HTTPS and a checksum from the same GitHub account detect transfer corruption and unexpected bytes; they do not protect against a compromised repository, GitHub account or build pipeline. They are not Authenticode publisher authentication. A future signed channel must verify its expected publisher and timestamp before execution; merely adding a certificate to setup does not establish that policy.

Updates require explicit native human actions. **Install and exit** requires confirmation before normal browser shutdown. The updater reverifies its private staged image, creates that exact image suspended while holding its file and ancestor handles, and starts it only after CEF, the broker and this instance's running marker have closed. Discarding a prepared update cancels only its own still-suspended setup process. Setup refuses installation while any other browser instance is running; no unrelated process or external MCP host is terminated. The installer replaces application files in the per-user program directory and retains the separate profile/vault and pairing configuration. Restart is a normal restart, not a seamless live-tab handoff. The installer rejects a version older than its recorded installed version. There is no service, scheduled updater, arbitrary update URL or forced unattended installation.

Security depends on shipping a maintained, matching Chromium/CEF distribution. Dependency selection and release publication remain maintainer-controlled. Follow the [CEF update and test procedure](BUILD.md) before releases. Do not add `--no-sandbox`, certificate-error bypasses, exposed debugging ports or credential logging to make a site work. The integration-only certificate fixture is compiled into a separate test build and is not a production bypass.

Use [GitHub private vulnerability reporting](https://github.com/Xero-05/xenon-browser/security/advisories/new) for suspected vulnerabilities. See the repository's [reporting policy](../SECURITY.md) for useful reproduction details and the maintainer response policy. Do not post passwords, pairing tokens, sensitive page captures or a working secret-exfiltration payload in a public issue. No audit, security response SLA or supported-version commitment is implied by this alpha.
