# Architecture

Xenon is a Windows x64 CEF browser with a local MCP adapter. The browser renders websites; the native broker authorizes and schedules work; a TypeScript process translates MCP tools into private local requests. Models and orchestration frameworks remain outside the browser. There is no built-in model, sampling dependency, public CDP port, or remote MCP HTTP listener.

```text
MCP client / agent host
  └─ bundled Node + TypeScript MCP stdio adapter
       └─ current-user Windows named pipe
            └─ native authorization and control broker
                 ├─ persistent client / workspace / account grants
                 ├─ per-tab input queue and ownership generation
                 ├─ metadata-only operation recovery journal
                 └─ asynchronous BrowserEngine interface
                      └─ persistent CEF tab controller
                           ├─ Chromium page, frames and request context
                           ├─ structured observations / finite input
                           └─ native vault and approved file boundary
```

## Components and trust

`adapter/src/server.ts` defines the public tool schemas. The released official MCP TypeScript SDK negotiates supported protocol versions; Xenon does not implement a separate protocol stack. Text JSON accompanies structured results, and screenshots use MCP image content. A text-only model can operate controls with rendered text labels; unnamed icons and visual content require image support.

The optional scoped host helper binds returned worker/workspace/tab IDs while leaving native authorization and evidence checks intact. `page.inspect` brackets a permitted screenshot with rendered observation checks, gives both targeting modes one observation ID, and obtains broker control metadata at delivery. It does not freeze page scripts or canvas. Journaled mutations carry native monotonic queue/execution timings and per-step batch durations. File discovery filters before pagination, uses bounded expiring opaque snapshots, and revalidates grants and file identity on continuation. A known relative file path can be resolved directly within an approved folder through the same native file policy, without recursive discovery. The adapter can explicitly export accepted public tool requests/results into a new private bounded directory; native recovery remains metadata-only, and modern stdio discovery probes create no export directory.

The server instructions classify all website content as untrusted data with no instruction authority, including images, dialogs and download names. The adapter sets a fixed `contentTrust` marker on page results, tab lists/creation, download lists and retained operation results. The native observation includes the same marker. Website claims cannot grant authentication or client/workspace/account/file authority, and cannot replace the user's task or the host's instructions. These instructions and provenance markers help clients preserve that boundary; they do not prevent a model from following a prompt injection.

`Broker` owns authority. The connection authenticates with a native-approved client ID and token. Model-supplied names and IDs never establish identity. The broker checks the authenticated principal, connected worker, granted workspace, tab membership, current owner, generation and observation before a page mutation. It rechecks grants when pending reads return. The adapter holds the token outside tool arguments and results.

`CefEngine` owns Chromium integration and marshals execution to the CEF UI thread. Its persistent per-tab DevTools observer and attached frame sessions survive changes of controller. The public surface exposes bounded browser operations, not arbitrary JavaScript, raw CDP, profile paths, cookies, network response bodies or OS input. Fixed internal JavaScript is used for actionability checks, form interactions, protected authentication and the main-world passkey gate.

The paired MCP client is the security principal. Multiple worker sessions behind one connection are scheduling identities within that principal; they are not mutually hostile tenants. Separate untrusted hosts should use separate pairings and workspaces. A workspace grant allows access to that profile's pages and existing authenticated sessions, even without a vault-account grant.

## Workspace and worker lifecycle

Creating a worker without `workspaceId` requires native automatic-workspace permission and remaining client quota, then allocates a distinct persistent workspace. CEF uses a separate request context and browser cache directory for each workspace. Cookies and site storage therefore stay separate by default. A worker may reuse a workspace already granted to its client. Native controls grant collaboration access explicitly.

Persistent request-context directories are direct children of the configured CEF root, named with opaque workspace hashes. This layout is deliberate: the Chrome runtime rejects deeper profile paths and can fall back to an off-the-record profile. Startup validates the configured context path, and the two-launch integration test verifies actual cookie/local-storage persistence.

The native initial workspace has a stable `native-default` identity. Native private workspaces use off-the-record request contexts and are omitted from persisted broker grants and the session index. They cannot be shared to MCP clients in this alpha.

Native **Close all tabs** is lighter workspace cleanup: the broker marks each listed tab closing, cancels and refuses its queued agent mutations, claims any control group closed in full for the human (a partly closed group keeps its owner), and asks the engine to close only after accepted finite input has drained. The engine also waits for guarded gestures to balance before closing. The workspace, its profile, grants and saved accounts remain. Like removal, it is not an MCP capability.

A live page cannot change request context, so moving a tab to another workspace is an explicit native reopen: the broker allows it only for an ownerless or human-owned control group with no pending handoff or accepted input, outside private workspaces and protected authentication. It opens the address as a new human-owned tab in the target workspace, then closes the original only if that check still passes. Moving a tab between native windows instead reparents its host window; the page, owner, generation and pause state are untouched.

Native **Remove workspace** protects Personal and requires human confirmation; it is not an MCP capability. The broker persists a permanent tombstone before revoking the workspace's grants, retiring its worker handles and canceling queued mutations. Accepted finite input and pending tab creation drain before the engine closes the workspace's tabs, cancels downloads and revokes file grants. Late popups and new creates are rejected. Saved vault accounts, downloaded files and original upload files remain. Native Controls identifies each tab's workspace, and new native workspaces open a blank tab.

After CEF acquires the user-data root's single-instance ownership on a later launch, a bounded cleanup helper attempts deletion of tombstoned persistent profile directories before any workspace contexts open. It validates hashed direct-child paths and retained file handles, refusing reparse points and multiply linked files. Permanent tombstones prevent reuse even when cleanup is deferred or refused; a retained cursor rotates future attempts. Locked or over-limit data can remain on disk. Memory-only private profiles require no profile-directory purge.

Fresh startup requests one `about:blank` tab. CEF's Chrome runtime couples session-cookie retention and last-window cookie cleanup to `session.restore_on_startup`. Persistent contexts retain the last-session value during ordinary operation. Before their first browser window, Xenon initializes the cookie network context asynchronously under that value without enumerating cookies, then applies the new-tab value only around synchronous CEF window creation and immediately restores the retention value. Concurrent creates wait for context readiness; ownership handoffs never touch these preferences. Chromium's self-restart hint is cleared at app initialization. This CEF-version-sensitive policy is covered by the normal Exit/restart regression and must be rechecked with dependency updates.

Workspace/profile persistence does not mean live renderer restoration. Pairings, workspace grants, vault grants and operation metadata survive a browser restart. Worker handles, input reservations and observations are process-local. Native **Restore last session** reloads eligible URLs from a current-user DPAPI-encrypted index into already known nonprivate workspaces, under human control. It excludes private/protected pages and does not recover a document's JavaScript heap, unsaved form values, scroll position, selection or sockets. This restart recovery is separate from live handoff, which preserves those states by retaining the loaded page.

Worker admission counts connected, nonretiring workers across all paired clients. The default global concurrent limit is 16; the human can set `--max-concurrent-workers=32` at native startup, with a supported range of 1–256. Each client's native policy adds its own ceiling across connections, defaulting to four for new clients. Neither limit is configurable through MCP or a lifetime creation quota. A disconnected resume checks both capacities; an already attached worker's same-connection resume does not consume an additional slot.

`workers.retire` permanently disables one worker handle, cancels its queued mutations and releases its admission slot immediately. Accepted finite input drains through the existing ownership barrier; pending callbacks and control-group references keep the retiring record alive until safe to remove. The result is `status: "retiring"` during that interval or `"retired"` once removed. Worker listing exposes `connected` and `state` (`connected`, `disconnected`, `retiring`), plus global `connectedWorkerCount` and configured `limits`. An already pending outgoing handoff can still settle to its authorized, connected recipient; retiring the incoming recipient instead releases the group after its input barrier. Retirement does not close tabs, recreate browser contexts, delete workspaces or revoke grants, and it never replays work.

After an adapter disconnect, a retained worker can resume while the browser remains running and concurrent capacity is available, then reacquire control and observe. The resumable cache targets 256 disconnected handles and evicts the oldest quiescent records. Pending input, callbacks or ownership transfers prevent eviction, so draining records can temporarily exceed the cache target; a separate ceiling of 1,024 total retained records bounds that pressure. These are retention bounds, not lifetime creation quotas. Handle eviction preserves live tabs, browser state, workspaces and grants. Retired or evicted handles require a new worker with the saved granted workspace ID. After a browser restart, also create a new worker, list any natively restored tabs, then request control.

## Parallel work and ownership

Different tabs can have operations in flight concurrently. A worker automatically owns the tabs it creates. Each tab permits one input transaction at a time, with a bounded queue. A single additional dialog-answer reservation lets the current unfrozen, unpaused owner dismiss a JavaScript dialog that is blocking the input transaction's reply. It remains journaled and is included in the handoff barrier. A short broker mutex protects metadata; it is never held waiting for a page action or network idle. Disk writes for action dispatch/recovery run on a separate worker. CEF still has its normal shared UI/event thread, so this is asynchronous concurrency rather than one OS thread per agent.

Website alerts, confirmations and prompts remain nonmodal native dialog records. For a human-owned or physically paused tab, a posted UI notification rechecks current status and the pending dialog, waits for held physical input to end, then shows Controls without activation and selects that exact tab. A dialog opened during human activity holds the pause until a native answer or closure, followed by the activity cooldown. The notice identifies website content and its origin and preserves the protected-authentication label. It never answers automatically. An unpaused agent-owned tab uses the existing MCP dialog operation; ordinary ownerless tabs do not surface a human notice. Multiple human dialogs are surfaced in sequence so a later tab does not replace the dialog being reviewed.

Both four independent MCP clients with three tabs each and four workers behind one connection with three tabs each are acceptance scenarios. Per-worker and transport budgets bound a noisy caller; the alpha does not promise strict latency fairness under arbitrary hostile load.

Handoff has three broker states:

1. **Freeze dispatch.** Verify the expected ownership generation and recipient's existing workspace access. Cancel queued, undispatched commands from the former owner throughout the tab's control group.
2. **Quiesce input.** Let accepted finite gestures complete and balance their pressed keys/buttons in every group member. Do not wait for network idle, cancel a navigation, stop page scripts, disconnect sockets, or recreate a profile.
3. **Commit ownership.** Atomically change only each group member's owner and ownership generation; clear the broker's observations. The commit makes no CEF or CDP call. The recipient observes separately afterward.

Related popups inherit a `controlGroupId`, owner and generation from their opener. A popup arriving during transfer also inherits its frozen state and pending recipient; it cannot escape the transfer. Existing group members can run separate input transactions concurrently under the same owner, but ownership changes wait for all of them. Closing the original opener does not remove the remaining group's boundary.

The recipient controls the same source workspace and tab. The tab is not migrated into the recipient's default profile. Handoff grants no additional workspace or vault rights. A pending handoff returns `handoffPending: true`; callers read control status until it commits.

Physical page activity pauses only the affected tab and preserves its owner and ownership generation. The engine reports activity and an advisory Unix-millisecond deadline, debounces idle for about two seconds, and keeps the pause active during held input, IME composition or a human-triggered dialog. The broker retains a monotonic activity epoch for the running tab, clears observations and cancels queued mutations. Each accepted command captures that epoch; continuation permits remain invalid after intervening human activity even once idle returns. Idle changes broker metadata without injecting input, restoring a queue or initiating an ownership transfer; it may let an already-requested handoff finish at its input boundary.

The owner must obtain a fresh observation after the pause before any new mutation, including navigation; tab close and dialog response are exempt from freshness but not from the pause. Freshness belongs to the observing worker. The engine still balances keys/buttons after interrupted finite gestures. Input already delivered cannot be recalled, and website scripts continue running. Native **Take ownership** explicitly transfers the control group to the human until a later explicit release or **Give to agent**; it is distinct from temporary physical activity.

Authenticated `control.activity` returns bounded status for the paired client's connected workers' owned, granted tabs. The adapter exposes an allowlisted snapshot as `xenon_activity` and the subscribable MCP resource `xenon://control/activity`, polling broker metadata at most once per second and notifying resource changes. Fields include owner/generation, `humanActivityEpoch`, `humanPaused`, `humanPauseUntil` and per-worker `requiresFreshObservation`; no typed values or website content enter the feed. Activity state is retained in memory for the tab's lifetime, not restored as a live tab after restart. Supporting notifications does not guarantee a particular host will interrupt an in-progress model turn.

`page.batch` is a native-broker plan of 1–16 element-targeted fill/select/check/click actions, limited to 64 KiB of UTF-8 step JSON. Admission validates every step before effects and uses one operation journal entry and one tab reservation. The broker executes the existing guarded engine commands serially; each step and continuation rechecks ownership, attachment, policy, human epoch, document and original observation. Targets retain the engine's rendered visibility, node/frame identity and actionability checks. A handoff freezes unstarted steps while the current finite gesture drains. The first failed step stops the plan; results distinguish completed responses, the unsuccessful step, skipped suffix and uncertain outcomes. No step is retargeted, re-observed, rolled back or automatically retried. Recovery persists only whole-operation metadata, not input text or step results.

## Evidence and actions

An observation combines Chromium accessibility nodes with DOM snapshot geometry, frame identity, provenance, capture start/end timestamps, document ID, observation ID and explicit coverage/truncation. Its default text surface is rendered content in the current viewport. Hidden accessibility names, `title`/`alt` attributes and descriptions are omitted; labels are drawn only from rendered visible text. Editable values are omitted. Query and wait use this same filtered evidence. An unnamed icon needs a screenshot, and content outside the viewport needs scrolling followed by a fresh observation. This limits hidden-content exposure without making visible text or images safe from prompt injection.

Bounds are reported in each frame's document CSS coordinates. The action path resolves the observed backend node again and checks geometry, visibility and occlusion before input. Screenshot coordinates require the corresponding screenshot observation and viewport.

Main-frame and attached out-of-process frame sessions are inspected. A failed frame is reported as unavailable or partial coverage. Rotated/skewed frame interactions fail explicitly. Canvas content generally requires a screenshot. Unsupported or inaccessible content must not be inferred from an empty node list.

Observations do not focus, scroll, or evaluate page JavaScript. They are not a transactionally frozen copy of a live site. A navigation, physical activity, ownership change, protected-login transition or overlapping dispatched mutation invalidates a pending result at the broker boundary. Reads during the human pause cannot establish fresh evidence. Chromium-side references also have document epochs and are revalidated when used. Scripts may still mutate a page between capture and dispatch; an error requests new evidence rather than inventing a replacement target.

Finite actions include click, hover, fill, select, check, page keys, scroll and drag. There is no cross-call held-key state. Input completion acknowledges the gesture; navigation dispatch acknowledges the navigation request. Neither proves that an order, payment, form submission or other website operation succeeded. Verify the resulting page separately.

Uploads accept an observed visible file input or visible upload entry, including verified StaticText references for non-semantic custom entries. The latter uses one element-reference click under temporary CDP chooser interception; DOM Text nodes use their exact single rendered range for visibility and hit checks, without promoting the parent container. A per-tab transaction matches Chromium's chooser session, frame and backend input node to the retained source document object; it never searches hidden inputs. Native grant resolution runs again before assignment, and continuation guards recheck activity, authority, document and authentication protection. Unsupported directory/File System Access pickers and different-frame delegation fail without selecting a file. Cleanup disables interception and releases the retained document object; it does not clear inputs or send cancellation events into a new owner's page. Completion waits for the pointer gesture to balance and reports activation separately from file selection. An assignment with an unverified response remains uncertain.

## Native login saving

A fixed monitor in Xenon's isolated renderer world recognizes top-level HTTPS logins with one current password. A login's scope is the password's form, or the page's controls outside any form, as on script-driven sign-in pages such as Google's. It remembers password fields after reveal and refuses ambiguous fields, new-password/one-time-code flows and submitter overrides. The native receiver independently checks the frame, origin, document/form identity, recent physical password-edit provenance and vault state. Private workspaces and agent-filled logins are excluded. The monitor is not a website API or an MCP tool.

A conventional submission (a same-origin POST to the current browsing context) is offered when it is submitted. A script-driven attempt (**Enter** in the login, a button press in its scope, or a form submission the page cancels to send it from script) keeps its edit provenance for a retry and becomes a deferred candidate: the engine offers it only after the main frame navigates, navigates within the document, or the monitor reports that the submitted password field left the page. A password field that stays visible is treated as a failed attempt; the deferred candidate expires after 30 seconds and a new password edit cancels it. Reveal, back, cancel, help, forgot and sign-up buttons and toggle controls are not attempts. The account is the single editable username or email field; otherwise one non-editable field marked as a username or email that a multi-step page repeats; otherwise the account a person typed with physical input on an earlier username-only step of the same origin in the same tab within ten minutes. That remembered account is native memory only and is cleared by agent mutation, native fill, workspace removal, tab closure and Windows lock. A password-only form with no known account is ignored when its origin already has saved accounts.

An eligible submission creates a DPAPI-encrypted candidate in native memory; it does not write an account. Candidates are limited to 64 with a ten-minute lifetime. The engine offers that submitted attempt without inferring authentication success from page contents; navigation or a removed password field only decides when a script-driven attempt is offered. The credential-entry origin is immutable: HTTPS SSO redirects and subsequent ordinary MFA input preserve the candidate without granting the destination site access to the password. An incorrect password can also produce an offer, so the prompt asks the human to save only if it is correct.

The engine notifies the native UI with an opaque candidate ID and the source window. Only these eligible notifications can create a modeless, source-owned Save/Update prompt; listing pending vault metadata is not permission to display one. The prompt is deferred while the source gesture or held physical input is active and while the source window is minimized or not foreground. Showing it does not activate or focus the window, block the UI loop or wait on unrelated agents. Its origin and masked username identify the offer without displaying a password.

Explicit native **Save** or **Update** consumes the candidate and writes the vault; **Not now**, closing the prompt, source-tab closure, non-HTTPS navigation, agent mutation, new qualifying password editing or Windows lock cancels it. Shutdown and expiry also discard pending candidates. Unchanged credentials are suppressed, newer submissions supersede older offers, and a stale update cannot overwrite an account changed since capture. Saving grants no MCP account rights by itself. Accounts reside in one shared vault per user-data root; each is in the Default or Sensitive group, chosen in the native prompt (Default unless the human ticks Sensitive) and changeable in Controls. The human grants a paired client a Sensitive account individually; a client or workspace with **Allow all Default passwords** can use every Default account, including ones saved later. Updates keep an account's group, and accounts from before groups existed migrate as Sensitive. Embedded cross-origin and unusual forms remain unsupported, as does automating MFA itself; the separate granted-account sign-in path supports its existing bounded username-first filling flow.

## Native human autofill

Native autofill is separate from both credential capture and MCP `auth.login`. The picker is a non-activating dropdown placed under the focused credential field, using a viewport rectangle the fixed metadata read returns with eligibility; it never receives values. Clicking an account, or **Enter** on a highlighted row, is the explicit native selection and confirmation; clicks in the first 500 ms are ignored. While it is open, native UI intercepts only arrow, **Enter** and **Escape** key-downs headed to its source window; other keys close it and reach the page normally. Qualified physical page input can request a picker about 150 ms after held input releases when an eligible field remains focused. As in Chromium, each left click (or touch/pen tap) on an eligible field can offer it again; keyboard input alone offers it at most once per document. This debounce is separate from the two-second agent idle boundary: fixed eligibility inspection and the native picker can run during that cooldown, while agent input remains paused. The toolbar key and Controls' **Fill selected login tab** request an offer for a tab without waiting for that cooldown. Both paths require an explicit native account choice. They use the shared vault without adding or requiring any client/workspace account grant, and have no MCP dispatch method.

The fixed isolated-world inspector returns a retained remote object containing the original document, form association, username/password nodes and value snapshots. Native code extracts only fixed eligibility/phase metadata and combines it with exact-origin vault account labels. An opaque native offer binds that object to the tab, document/activity epochs and HTTPS origin; at most 64 offers exist, each with a two-minute lifetime. The conventional two-field POST phase accepts absent autocomplete attributes, including the public CWL form shape. A unique explicit username takes precedence over unrelated text fields; telephone usernames and text inputs explicitly marked `current-password` are recognized. Separate username and password phases require explicit `username` and `current-password` autocomplete semantics; each fills only the current phase and never advances it. Visible inputs with no form association are treated as one conservative synthetic group, requiring these explicit semantics for every selected credential field. The document and null form association remain bound through confirmation; ambiguous groups and OTP/new-password fields are refused. This supports a Google-shaped username step without adding form-less agent submission. See [credential detection comparison](CREDENTIAL_DETECTION.md).

Confirmation consumes the offer before any setter. The engine emits human activity and seals authentication before decryption, preserving owner and generation while canceling queued agent work and invalidating pending evidence. It waits for the count of in-flight guarded actions to reach zero so finite input can balance. The native authentication guard permits this transaction during its own pause while retaining epoch, activity, origin, lock, physical-gesture and workspace checks. Its captured request generation makes cancellation durable across lock/unlock. The secret is fetched only after that boundary; an unavailable account fails without filling.

The bound fill script rechecks node/document/form identities, exact form action, field types and autocomplete, visibility, editability and unchanged human values. It refuses GET, cross-origin/other-context forms, ambiguity, overlays, OTP/new-password fields and nonempty passwords. Both original values are set before page input/change handlers run; replacement fields never become new destinations. After those handlers, success requires the original nodes still to be connected to the same form/document with the requested values. No submission or retry is performed. Fixed results reach native UI; credentials and retained renderer objects never enter MCP responses. Protection remains until the normal native resume/navigation boundary.

## Passkey gate

Chromium and the Windows authenticator perform every WebAuthn ceremony; Xenon adds a gate in front of them. For the main frame and each attached frame session, the engine adds a main-world binding and installs `passkey_guard_script` with `Page.addScriptToEvaluateOnNewDocument`. The script wraps `CredentialsContainer.prototype.create` and `get`, sends a bounded request (`operation`, `mediation` and an opaque ID) for each `publicKey` call and forwards the call unchanged only when native code answers yes. Native code accepts messages only from tracked main-world execution contexts and parses them against a fixed schema.

Installation precedes website script where Xenon controls the start. A tab created for a website first commits `about:blank`, which gives the DevTools session a renderer, and loads the requested URL only after the wrapper's installation reply; the creation reply waits until that load has started, and `Page.resetNavigationHistory` removes the placeholder entry once the real navigation commits. Frame sessions are auto-attached with `waitForDebuggerOnStart`, so each cross-origin frame stays paused until its wrapper is installed; other auto-attached targets resume immediately. Popups opened by a page are created by Chromium with their URL, so a popup's first document can run before its wrapper is installed.

The decision is per tab. The broker's `human_controls` check covers human-owned tabs with no handoff pending; those are unrestricted. Elsewhere, `PasskeyGate` allows a modal request only within 15 seconds of the human's physical input routed to that tab, and any agent page command executed for the tab ends that window. Conditional (autofill) requests are refused outside human control. Each forwarded modal ceremony is held, at most eight at a time, until the wrapper reports that it settled, its execution context is destroyed or 10 minutes pass. While one is held, human activity stays busy, so the broker keeps agent input paused without changing the owner. The first refusal in a document emits `passkey.refused`; the broker reports `passkeyNeedsHuman` until `tab.navigated`.

## Recovery and retention

Mutation calls carry a caller-generated `operationId`. The in-memory journal deduplicates the same request and rejects conflicting reuse. Before dispatch, a metadata-only recovery marker is flushed and atomically replaced on disk. After queuing onto CEF's UI thread, the engine invokes a trusted broker permit callback immediately before execution and again before later effects in asynchronous actions. The callback rechecks connection, grants, ownership, generation and activity epoch; repeated successful checks record only one dispatch. An initially denied permit produces `not_dispatched` without a browser command. Denial after dispatch stops further effects while allowing necessary balancing and cleanup, and preserves actual or uncertain outcome status. Completion metadata is persisted asynchronously, so a crash can conservatively leave an otherwise completed action uncertain.

Recovery never replays an action. An unresolved marker becomes `OUTCOME_UNKNOWN`; a terminal marker retains its status but returns `RESULT_NOT_RETAINED` because arguments and page output are not saved. The journal contains operation/principal/tab IDs, state and dispatch status. In-memory results exist only during the browser process lifetime.

The journal is bounded to 4,096 entries and evicts terminal entries. Deduplication is therefore limited to retained entries; it is not an indefinite exactly-once guarantee. Use fresh IDs and inspect both operation status and the page after a timeout. Tab creation is not journaled and must also be checked before retrying an uncertain create.

Other current limits are 64 tabs, 16 queued mutations per tab, 32 pending mutations per worker, 16 simple actions per batch, 64 outstanding requests per pipe connection, 1 MiB per request, 16 MiB per response and 32 MiB buffered outgoing data per connection. A bounded batch occupies one mutation reservation and journal entry. The named-pipe server supports at most 32 instances. Limits are alpha safeguards, not measured capacity claims. Retiring or disconnecting a worker frees its concurrent slot; ongoing work does not require a browser restart to replenish a lifetime quota.

## Verification and remaining work

Native tests use a fake asynchronous engine to exercise authorization, generations, popup-group handoff without engine calls, queued UI-dispatch cancellation, dialog/input reservations, private workspace persistence, deduplication, restart uncertainty, protected-observation races and revoked metadata reads. Real Windows pipe tests cover authentication, correlation, malformed messages, exclusive listener ownership and shutdown. The live CEF suite exercises parallel clients/workers, profile isolation, page interaction and preservation of document identity, form state, selection, scroll position and a WebSocket during idle handoff. See [build and test instructions](BUILD.md).

This alpha has bounded coverage rather than a claim of universal web automation. Restoration of live renderer state after process exit, extension UI integration, broader password-manager heuristics, production-grade resource scheduling and a cross-browser task benchmark remain future work. The native Save/Update flow has renderer-monitor and encrypted-vault tests, and human autofill has production-script tests; end-to-end physical typing and credential-prompt interaction remain manual acceptance work. Changes to the CEF runtime require security maintenance and a fresh acceptance run.

## Native shell and client policy

The pinned sandboxed CEF runtime renders windowed Alloy content in persistent native tab hosts. Xenon owns one or more top-level windows, each with a Chromium-style toolbar (navigation, omnibox with saved-account key and bookmark star, ownership chip, Extensions, Controls and menu buttons) above grouped vertical tabs. Omnibox suggestions are ranked natively from the selected tab's workspace bookmarks and history, using a per-workspace index that new visits update in place and other metadata changes rebuild on next use, and drawn in a non-activating owned popup so keyboard focus stays in the address edit. They make no network request, have no MCP surface, and complete inline only after a printable character typed at the end of the text. The site-information button reads the visible navigation entry's TLS status (at most every 500 ms, and only when that entry matches the main frame's origin) and opens an activating owned bubble built from real child controls. The engine supplies certificate principals and DER bytes for the Windows certificate viewer, cookie metadata for the site's host and its subdomains (names, domains, paths, expiry and flags; values are never read), per-origin content settings and, through the page's own DevTools target, storage use. Every change rechecks that the tab still shows the bubble's origin outside protected authentication. Deleting cookies or site data uses CEF's cookie manager and `Storage.clearDataForOrigin`, and counts as human page activity. None of this has an MCP surface. While the main frame shows Chromium's certificate-error page (a committed load error in the certificate range), the Chrome Help Center request from its **Learn more** link loads Xenon's user-guide section in that tab instead; the page's other requests, such as a captive portal's sign-in page, are unchanged. After any main-frame load error the engine also runs the fixed main-world `hide_enhanced_protection_script`, which adds a style rule hiding Chromium's enhanced-protection suggestion (its settings link needs a Chrome browser window) and acts only in Chromium's error document, `chrome-error://chromewebdata/`. Selecting a tab raises its host; grouping/collapse and ownership changes never hide, reparent, focus or recreate its page. Agent-created tabs stay beneath the selected host, in the window already showing their workspace; popups join their opener's window. Only an explicit human tab drag or **Move tab to window** reparents a host, after which CEF is told the window moved. Find floats over the page rather than resizing it. Full screen (**F11**, or a page's fullscreen request in the selected tab the human controls, reported through `OnFullscreenModeChange`) removes the window frame, hides the toolbar and sidebar, and sizes the hosts to the monitor; the page's own full screen is ended with `ExitFullscreen` on **Esc** or a tab change. Site icons come from `OnFaviconURLChange` and `DownloadImage` as bounded premultiplied bitmaps drawn in the tab list. Non-web navigations and popups never load: `external_protocol.hpp` decides which schemes may reach a non-activating native prompt, under the passkey gate's person-or-recent-input rule, and a confirmed link is escaped and passed to `ShellExecute` off the UI thread. Display-capture requests use the same rule and the permission panel; while a tab captures, agent screenshots of it fail. Launch links (`launch_urls.hpp`) open in the first Personal tab, or reach an already-running browser through a message-only window named from the data folder, since Chromium's relaunch notice carries only CEF's own switches. Bookmark folders, per-visit history deletion and import (`browser_import.hpp`) change the workspace's DPAPI-encrypted metadata; Clear browsing data also uses CEF's cookie manager and, through one of the workspace's tabs, `Storage.clearDataForOrigin` and `Network.clearBrowserCache`, and counts as human page activity in every tab of the workspace. The bookmark manager, history, import, Clear browsing data and Settings are native windows without an MCP surface. Native tab-switching and focus shortcuts are passive input; reload shortcuts count as page intent, like F5. Touch and pen arrive as posted pointer messages to the page window and hold the pause until the contact lifts; hover stays passive. A precision-touchpad scroll or pinch is handed to DirectManipulation after a sent `DM_POINTERHITTEST`, which a thread `WH_CALLWNDPROC` hook observes; its hold ends when Windows no longer reports the contact or after five seconds. Monochrome System/Light/Dark themes use Windows high-contrast colors when enabled. Native-hosted Alloy pages take `prefers-color-scheme` from Chromium's process-wide native theme, not `CefRequestContext::SetChromeColorScheme`, so Light and Dark start CEF with `force-light-mode` or `force-dark-mode` and System leaves Windows in control. Chromium reads those switches once; a runtime theme change reaches web content after restart. Teal indicates an available agent owner, orange indicates its human-input pause, and gray indicates unavailable or human ownership. Text labels and protection badges accompany those colors.

Controls separates Clients, Workspaces and Passwords. Approve/Deny handles pending pairing requests; approved clients remain paired. Each workspace has a persisted display name. Its configuration window controls per-client access, capabilities and inherited-resource selections; the tabs table independently filters by selected workspace. Configuration APIs are native-only. MCP listings expose names, effective capabilities and client quota metadata, never configuration mutation endpoints.

Rounded buttons and vector icons render with antialiasing at each window's DPI. Hover shows a neutral gray fill and native tooltip; list selection uses gray. Only available, unpaused agent owners have background tab outlines. An owner's help request (`attention.request`, broker metadata with no engine call) pulses its tab, or its collapsed workspace row, orange until the shell observes the person present: the tab selected in the foreground window and system input after the request arrived (`AttentionNotices`). The shell then calls the native-only `attention_seen` and keeps a steady orange outline. New requests flash a background window's taskbar button and, when the opt-in setting allows, show a tray-balloon Windows notification whose selection restores the window and selects the tab; alerts are limited per tab. The selected entry connects to its page frame, whose footer reserves room for the bottom curves. Theme and sidebar width persist atomically in `ui-settings.json`; the sidebar supports drag, double-click reset and keyboard menu actions within 180–480 DIP and the page's minimum width. Explicit human resizing changes the viewport; ownership and hover refreshes do not run page layout.

The shell buffers frame painting and invalidates only the divider grip when divider hover changes. Workspace disclosure uses chevrons, and background tab hover has a neutral fill. Native selections use a small keyboard-only focus mark rather than a dashed rectangle. Address drafts survive toolbar refresh and focus moving to Go; Enter/Escape in address and find edits reach their subclass before Windows dialog translation. Escape discards an address draft, and explicitly selecting another tab synchronizes its address.

Page-owned native popups have a separate visibility boundary (`page_popup_guard.hpp`). Windows promotes their owner from a child page window to the top-level shell, so sibling tab stacking alone cannot contain them. A UI-thread creation hook retains the original tab host before that promotion, then suppresses popup show requests unless that source is selected in its visible, non-minimized foreground window. Selection changes and shell refresh hide existing ineligible popups. A queued native close lets Chromium retire the popup after its show callback returns, including its renderer-side open state; it rechecks visibility and eligibility before closing. Source destruction invalidates a lifetime token so a reused HWND cannot authorize an old popup. This policy does not depend on agent ownership and does not hide, resize or reparent page hosts. In-page menus remain page content; native background selects can still use the supported `select` action.

Sidebar groups include all broker workspaces, even those without live tab hosts. Selecting an empty group requests a blank human tab through the existing native broker API; it never automatically reloads a saved session. Visible close buttons and middle-click close their specific tab without selecting it first. Ctrl+W and sidebar Delete provide keyboard access. CEF completes tab closure before the broker and shell remove it; workspace records and profiles remain.

New clients are read-only with automatic creation disabled and quotas of four connected workers and four automatic workspaces. Effective capabilities intersect client ceilings with workspace permissions. Manual sharing starts read-only; automatic workspace grants inherit enabled capabilities and client resources. Client-level file/folder and exact-HTTPS-origin account grants can be inherited live and restricted per workspace. A client's Default-group grant is inherited like its individual account grants; a workspace can also grant the Default group directly. The broker resolves Default-group access through a native vault lookup of the account's current group and stored origin on every check, failing closed when the vault is locked or the lookup fails. Revocation invalidates queued actions, asynchronous continuations and late results. CEF download callbacks enforce effective download permission, including indirect page downloads. Quotas count connections collectively and persisted workspace creators; lowering quotas blocks admission while retaining existing work. Version-1 state migrates without changing IDs, pairings or grants: legacy clients retain their capabilities/global worker limit and historical workspaces have no creator quota count.

Legacy copied Chromium extensions are managed natively by `ExtensionStore`. A chosen unpacked Manifest V3 folder is validated, copied into a randomly named folder under the user-data root (links, reparse points, oversize trees and pages outside the extension are refused), and recorded with its Chromium ID. At startup the enabled folders are passed to Chromium with `--load-extension`, so they load into persistent workspace profiles; off-the-record private profiles do not run them. Changes take effect after restart, and removal of a loaded extension's files is deferred to the next start. In ordinary Alloy tabs the engine allows `chrome-extension://` navigation only for legacy IDs loaded this session, and only native UI opens those pages; agent reads and input already refuse every non-web page.

The default extension manager uses `cef_extension_manager.cpp` to embed a Chrome-style `CefBrowserView` with Chromium's real `chrome://extensions/` WebUI and Store APIs in a Xenon sidebar tab, sharing the selected persistent workspace request context. Its Views container is frameless and has `CEF_CTT_NONE`; the empty hidden container is parented once into a native Xenon content host before the browser is created. Xenon's shell owns navigation, sizing, tab selection and closing. Native-only tab metadata and commands are separate from broker tabs, evidence and session recovery; management tabs cannot move between workspaces. Normal install, permission, enable/disable and update handling belongs to Chromium within that profile. Fixed top-level origin policy is in `extension_manager_policy.hpp`; no JavaScript Store shim, unsafe debugging flag or MCP method is added. `cef_default_client.hpp` resolves CEF-created browsers once their context is known: manager-context Chrome views retain the native client while ordinary popup/print clients keep the existing engine handling. Chromium-created auxiliary browsers used by post-install UI are kept outside the visible inventory and broker, prevented from navigating, and held in a separate per-workspace lifecycle map. Their native windows suppress show requests. Rejection takes one extra UI queue turn before Chromium schedules its own destructive close, allowing the already-queued install watcher to finish while its active tab still exists; there is no timer-based grace period. Auxiliary closure is tracked through `OnBeforeClose`. Management views and these auxiliary browsers are drained on workspace removal and before CEF shutdown. Native chrome opens the appropriate workspace's manager; Controls and private-window entry points use Personal. Ordinary Alloy page hosts remain in place, so full extension toolbar/tab-API compatibility is not implied.

The shell displays the manager URL as `xenon://extensions/` and resolves that alias only from native address-bar input. Chromium keeps its real privileged WebUI origin. A per-view native navigation policy admits the exact HTTPS Google account service only after a Store navigation, allowing account routes back to the Store; returning to the manager or an extension page revokes that allowance. Account pages remain outside broker inventory and never receive manager presentation code. The embedded window is shown through `CefWindow::Show()`, which updates Views/compositor visibility; a Win32-only `ShowWindow()` can leave the loaded page blank. The test-only fixture checks Views visibility and captures the management HWND to require actual painted content, in addition to DOM/API readiness and host geometry.

`extension_manager_ui.hpp` supplies fixed presentation code for that main WebUI frame only. It follows the manager's known shadow roots to hide product artwork and normalizes existing exact-origin Store anchor targets to `_self` before their native click action. This preserves the current workspace and native Store APIs while avoiding default new-browser creation, which the management client rejects. Lazy drawers and Lit rerenders are handled with document-scoped observers; navigation discards those observers. This presentation code does not edit Chromium resources, and external Store/extension documents receive no customization script. Engine changes are applied separately through the tracked source patch below.

The compact native extension panel (`cef_extension_panel.cpp`) uses `cef_extension_catalog.cpp`: a bounded, never-shown, nonactivating Chrome-style WebUI helper queries fixed `chrome.developerPrivate` metadata APIs in the selected persistent context. Only the native-derived HTTP(S) origin is passed as JSON. Icons, enabled IDs, names, pin state and declared access options return to native controls; no website DOM is queried. The browser, helper window and hidden parent finish closing before delivery. Source document epoch, URL, workspace, foreground window and protection state are rechecked before effects. Private contexts return an empty list. Helpers never enter visible or broker inventories; removal and shutdown drain them.

The SHA-pinned `cef-extension-actions.patch` adds a versioned native-only export, loaded through `extension_action_engine.hpp` without changing the public CEF ABI or bootstrap. Xenon explicitly registers ordinary non-private Alloy tabs. Chromium's action runner provides user-click grants, dynamic popup resolution and `onClicked`; a real `ExtensionViewHost` with popup view type runs inside a desktop Views bubble anchored to Xenon's toolbar. Source navigation/destruction, extension unload, outside dismissal and shutdown retire the popup. Registered tabs participate in permission-scrubbed `tabs.query` and native tab metadata, scoped to the exact profile and source window. Site controls use Chromium's permission services and `ExtensionsMenuAccessControl`; narrowing access clears temporary grants. Human actions invalidate agent evidence without transferring ownership. `chrome.action.openPopup()` routes to the same genuine popup host and completes its callback only after load; it never runs the human action runner or grants `activeTab`. A native guard rechecks the live selected source, exact context, authentication/protection and foreground window before extension-requested surfaces. Side panels use `kExtensionSidePanel` hosts in a native child Views widget with a close header and shell-reserved resizable bounds. Chromium side-panel options, gesture validation, open/close requests and events remain authoritative. Global panels rebind within the same profile/window; contextual panels hide outside their tab. Cross-workspace/private selection and protected interaction close the surfaces. These API routes bypass only Chrome window-controller lookup, never permission checks. Full Chrome window/tab manipulation remains limited. See [engine build constraints](BUILD.md#extension-action-engine-patch).

The previous copied-extension facility remains available as **Legacy copied extensions**. Its link dialog uses `web_store.cpp` for exact-link parsing, bounded fixed-origin HTTPS transport, CRX3 developer/Web Store signature verification and ZIP structure/path inspection. `cef_extension_installer.cpp` decompresses verified bytes on the download worker and checks file sizes and CRCs, producing an immutable in-memory permission-review package. Only the native **Install extension** action passes that package to `ExtensionStore::install_web_store`; cancel, session lock and shutdown discard it. Managed installation preserves the signed developer key for a stable Chromium ID and uses the existing restart/disable/remove lifecycle. These legacy copies retain their global startup behavior and have no automatic updater; the new per-profile manager does not silently rewrite their registry or profile data.

Native bookmarks/history use per-workspace DPAPI-encrypted metadata. Existing Chromium bookmark JSON and history SQLite are read without modifying their original files. Private metadata stays in memory; new protected-authentication visits are excluded.

A hit-test-transparent native agent cursor remains outside page screenshots and never moves the Windows pointer. Its white arrow uses the ownership color for its outline, with a soft outward glow; the selected tab and page frame share a continuous inward glow. Gray frames have no glow. Premultiplied-alpha native overlays preserve page geometry and pass input through. High contrast keeps solid outlines without glows. The cursor hides throughout the human-input pause (including held input, IME and human dialogs), returning when the pause ends. Visual parking, synchronization, pause and resume dispatch no website input. Authorized pointer actions use bounded accelerated curves, locally generated variation and safe element interiors; screenshot coordinates remain exact. Authority is checked on every step, target geometry is revalidated before press, and interrupted held input is balanced without replay.
